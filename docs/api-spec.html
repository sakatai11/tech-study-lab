実装前に確認する API 仕様

エンドポイントごとに「何を送ると、どんなJSONが返るか」を実例で示します。フィールド定義・成功応答・エラー応答・実装状態を、画面実装とAPI実装の両方から同じ形で参照できます。

この文書の位置づけ

画面構成とユースケースの一次ソースは 設計文書 §7.3、エラー方針は §10.6、レート制限は §10.3.1 です。このページはHTTP入出力・レスポンス実例・実装状況を参照しやすくするための仕様カタログです。

掲載しているJSONは、共有Zodスキーマと route 実装から起こした代表例です。値そのものは固定ではありません（形と型が契約です）。

最初に読むなら、この3点

1. 状態を見る

implemented はrouteと共有Zodスキーマの実装済み、planned はDTOが未確定です。

2. 成功だけでなくエラーを見る

各エンドポイントのレスポンスはステータスコードのタブで切り替えられます。入力不備・対象なし・レート制限・内部エラーの実例を先に把握してください。

3. Zodを正とする

実装済みの契約は packages/shared/src/schema/api.ts をAPIとフロントで共有します。掲載例と食い違う場合はスキーマが正です。

共通規約

パスと形式

現時点ではAPIバージョンのプレフィックスはありません。リクエストとレスポンスはJSON（application/json）で、本文のない GET にJSON bodyは送りません。

ユーザーコンテキスト

API middleware が固定の user_id を権威的に注入します。クライアントは user_id / userId を送らず、レスポンスにも含めません。

2つのentrypoint

公開HTTPは CORS → Access検証 → userContext → routes。web Server loader が使う Service Binding の InternalApi は userContext → routes のみで、同じrouteを共有します。

認証（公開entrypoint）

Cloudflare Access の Cf-Access-Jwt-Assertion を Worker 側で検証します。未設定・欠落・不一致はすべて 401 UNAUTHORIZED。loopback URL かつ Access 未設定のローカル開発のみ bypass します。

エラー形式

routeのエラーは原則 { error: { code, message } }。ただし入力検証の400は現時点で zValidator の既定形式（{ success: false, error: { issues, name } }）です。

永続書き込みのレート制限

設定上限は POST /answers が60秒あたり60回、POST /lesson-views が60秒あたり30回。超過時は 429 ＋ Retry-After: 60、limiter 自体が使えない場合は fail closed で 503 です。Cloudflare location（PoP）ごとのカウンタで eventually consistent な abuse reduction であり、厳密なグローバルquotaではありません（§10.3.1）。

共通エラー応答

各エンドポイントのレスポンスタブにも同じ形で掲載しています。ここは形式そのものの一覧です。

400 Bad Request（zValidator 既定）

リクエストbodyがZodスキーマに合わない場合。{ error: { code, message } } ではなく safeParse の結果がそのまま返ります。strict なスキーマでは未知フィールドも unrecognized_keys で弾かれます。

401 UNAUTHORIZED

公開entrypointのAccess境界。設定不足・トークン欠落・署名/issuer/audienceの不一致をすべて同じ応答に潰し、失敗理由を外に出しません。Service Binding 経由の InternalApi では発生しません。

429 RATE_LIMITED

永続書き込み（POST /answers / POST /lesson-views）のみ。service を呼ばないため answer_logs・lesson_views・srs_states は変化しません。Retry-After: 60 が必ず付きます。設定上限を超えた全リクエストが429になる保証はなく（PoPごと・eventually consistent）、クライアントは429を受け取ったときに対処します。

503 RATE_LIMIT_UNAVAILABLE

レート制限 binding の呼び出しが失敗、または実行環境に無い場合。可用性より保護を優先して fail closed とし、service / D1 path を呼びません。

500 INTERNAL

未知の例外は onError がまとめて500へ写像し、詳細メッセージを外へ出しません（Workers Logs 側にのみ記録）。全エンドポイント共通です。

404 QUESTION_NOT_FOUND

POST /answers のみ。同期済みの questions に questionId が無い場合に、service のドメインエラーを route が写像します。

POST

/answers

implemented

1問の解答をサーバーで採点・記録し、SRS状態を更新します。演習・復習・誤答のみ再挑戦で契約は共通です。

認証: Access（公開entrypoint） レート制限: 60秒あたり60回（設定上限） Zod: answerRequestSchema / answerResponseSchema

リクエスト

フィールド型必須制約・意味
questionIdstring必須1文字以上。content 由来の問題ID。
selectedIndexnumber必須0〜5の整数（choices は最大6）。
responseTimeMsnumber任意0以上の整数。未送信でも採点は成立します（平均反応時間の集計用）。

本番の公開ホストへ直接叩く場合は Cloudflare Access の cookie / JWT が必要です（未添付は 401）。

レスポンス

フィールド型意味
isCorrectbooleanAPIが questions.answer_index と照合した採点結果。
correctIndexnumber0〜5の整数。解答後に解説を出すため、採点結果と同時に返します。

誤答も 200 です。採点結果はHTTPステータスではなく isCorrect で判定します。解答ログとSRS更新は同じ db.batch() で原子的に書かれます。

strict なスキーマのため、userId など未知フィールドを含めても 400 になります。

content と D1 の同期がまだのときに起きます。解答ログとSRS状態は書き込まれません。

60秒の固定窓で設定上限（60回）を超えたときに返します。カウンタはPoPごと・非同期更新のため、超過後のすべてのリクエストが必ず429になるとは限りません。429を返した場合は service を呼ばないため書き込みは発生しません。

公開entrypointではAccess検証に失敗すると route に到達せず 401 UNAUTHORIZED を返します。

なぜAPIで採点するか: クライアントに正解を持たせず、APIが questions の正解と照合するためです。

追加API

implemented · route / Zod実装済みplanned · DTO未確定実装済みのAPIは共有ZodスキーマとD1 integration testまで確定しています。planned は目的・成功ステータス・返す予定の値のみを先に共有し、フィールド名と型は各実装Issueで確定します。

後続Issueで必ず更新するもの

各APIの実装に着手するときは、返却値を共有Zodスキーマで確定し、このページのレスポンス例・フィールド表・実装状態も同じPRで更新します。APIのIF（URL、HTTPステータス、JSON形式、エラー形式）を実装だけで先に変えないでください。

この節のAPIはいずれも認証・エラー形式が Walking Skeleton のAPIと共通です（共通エラー応答）。すべて読み取り専用のため、永続書き込みのレート制限（429 / 503）は対象外です。

analytics の3 APIは Issue #32 で実装済みです。週次データは UTC の直近7日を0埋めし、誤答ランキングは2回答以上の問題を対象に最大10件を返します。忘却曲線と復習タイミングの計算APIは提供しません。
