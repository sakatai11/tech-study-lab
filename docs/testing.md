# テスト方針

テストをいつ・どの層に・どこまで書くかの方針。契約の理由と境界は [ADR](./adr/README.md)、層と依存方向は [`docs/design.md`](./design.md) が持つ。本書はそれらを再掲せず、検証の進め方だけを定める。ADR とテストの関係、契約の優先順、テスト名の `[ADR-NNNN]` の付け方は [ADR の運用](./adr/README.md) に従う。

## 契約先行の選択的 TDD

すべての層を一律にテストファーストで実装せず、**契約先行の選択的 TDD** を採用する。バックエンドは service を中心にテストファーストとする。フロントエンドは UI を実装先行とし、ロジックと状態遷移をテストファーストとする。

### バックエンドの開発順序

1. 関連する ADR で契約を確認する。契約を新設・変更する場合は、実装やテストより先に ADR を作る。層と依存方向は design.md §4.3 で確認する。
2. `packages/shared` の Zod スキーマで API の入出力契約を定義する。
3. Hono・D1・Drizzle に依存しない service の振る舞いを、インメモリ fake deps を使ったテストで先に記述する。
4. テストを満たす最小限の service 実装を書く。
5. 薄い route と DAL を実装する。
6. Cloudflare Workers ＋ ローカル D1 の貫通テストを、重要な経路に絞って追加する。

## 層ごとの検証範囲

### バックエンド

- **純粋関数・SRS**: 厳格な TDD を行う。SRS は最重点のテスト対象であり、初回解答・連続正解／不正解・間隔の上限下限・日付境界を網羅する。
- **service**: 原則としてテストを先に書く。正常系だけでなく、問題未存在、既存状態の有無、正解・不正解などの分岐を検証する。依存はモックライブラリで置き換えず、service が宣言するフラットな deps 型を満たす fake を渡す。
- **Zod スキーマ**: 境界値と、拒否すべき入力をテストする。型だけでは保証できない実行時の契約を、有効系と無効系の両方で固定する。
- **route**: `zValidator`、middleware、ステータスコード、エラーの写像など HTTP の契約を検証する。service の振る舞いを route のテストで重ねて検証しない。
- **DAL**: Drizzle のクエリを Node 上で細かくモックしない。`@cloudflare/vitest-pool-workers` と、migration を適用したローカル D1 で、実際のクエリ・制約・upsert・`db.batch()` を検証する。
- **貫通テスト**: 主要なユースケースごとに少数置く。`POST /answers` では「入力検証 → 採点 → 解答ログの記録 → SRS の upsert → レスポンス」を最低1本通す。
- **Workers binding**: Rate Limiting などの platform binding は小さい interface に隔離し、単体テストでは固定時計の fake に差し替える。route の結合テストでは拒否・例外を返す fake を渡し、エラー応答と D1 が変わらないことを確認する。platform 側の結果整合性を、ローカルテストの正確な上限と取り違えない。現在のテスト基盤で実 binding を供給できない制約と、その代わりの確認手順は [調査記録](./investigations/2026-11-07-rate-limit-binding-in-workers-tests.md) にある。

### フロントエンド

- **UI・スタイル**: モックアップと、関連 ADR・[デザインシステム](./design-system.md) を確認してから実装する。ブラウザで表示・レスポンシブ・操作を確認した後、重要な振る舞いだけをテストする。Tailwind のクラス名や内部の DOM 構造を固定するだけのテストは書かない。
- **presentational component**: 原則として実装を先行する。条件分岐やユーザー操作がなく、上位の統合テストで十分に検証される場合は、テストの追加を必須にしない。
- **純粋変換・mapper・ViewModel**: 入出力と境界条件が明確なため、原則としてテストを先に書く。content／API DTO の join・sort・filter と、正解データをクライアント向け ViewModel に混入させないことを重点的に検証する。
- **hook・reducer・状態遷移**: 原則としてテストを先に書く。画面フェーズの遷移、問題送り、最終問題、選択肢のロック、スコア集計、`wrongOnly`、二重送信の防止、エラーと再試行を検証する。
- **Server loader**: 単純な委譲は詳細にテストしない。複数データの join・sort・filter・ViewModel 化など、表示の仕様を担う処理を検証する。
- **API wrapper**: 薄く保ち、Hono RPC ライブラリの動作をなぞる単体テストは書かない。呼び出し条件やエラー変換に独自のロジックがある場合だけ検証する。
- **ページ統合・E2E**: 細かなコンポーネント単体テストを増やす代わりに、ユーザーが観測できる振る舞いを少数の統合テストで検証する。「教材表示 → 解答 → 即時採点 → 結果表示」はブラウザで貫通を確認する。

### バグ修正

自動テストで安定して再現できる場合は、失敗する回帰テストを先に書く。CSS やブラウザ固有の表示崩れなど、安定した自動化が難しい場合は、修正前後をブラウザまたはスクリーンショットで確認する。

## 共有スキーマを変えるとき

`packages/shared` の Zod スキーマは API の `zValidator` と web の型推論の両方から使われる。変更したら `pnpm typecheck` で両方の利用箇所を確かめ、スキーマのテストに有効系と無効系を加える。DB スキーマの変更は `d1-migration` スキルの手順に従う（migration の扱いは ADR-0011）。

## テストの書き方

- テストは実質を検証する。実装をなぞるだけのスナップショット的なテストや、常に成功する形だけのテストを書かない。
- 実装のバグを隠すために期待値を弱めない。期待値を変える場合は、根拠となる ADR を明記する。
- 日付・乱数に依存するテストは、`vi.useFakeTimers()` や seed の固定で決定的にする。
