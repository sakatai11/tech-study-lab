# Jevによる設計参照チェックのPoC（Issue #255）

初回評価は2026-10-17、正式な人手評価の記録は2026-10-18（いずれもJST）。推奨は**補助用途の試用を続け、評価を改善して再検証する**。固定24組でJev単独は人が確認したラベルと23/24組一致し、今回の確認時間はAPI処理込みで377.4490秒短かった。ただし同一人物・同一データへの先行露出と順序効果を分離できないため、本格採用とCIの必須ゲート化、自動承認は見送る。ローカルの実測記録は揃ったが、既存PRへの反映とCI確認はまだ実施していない。

## 対象と構成

参照元は明示指定した `AGENTS.md`・`.ai/review-guidelines.md`・`.ai/rules/*.md`。対象は `docs/design.md` の章と `docs/adr/` のADR。パス・章番号・anchorの解決はコードで行い、解決した主張と参照先の意味だけをChoiceで判定する。既存の存在検査は保持する。アプリの実行経路や設計契約は変えない（ADR-0001の境界内）。Graph用のTOMLパーサーも変更しない。

- 実装: `scripts/check-design-references.mjs`、`scripts/design-references.mjs`
- モデル: `jev-1.13.0`（可変aliasを使わない）
- 質問: `design-reference-v1`。質問本文・4分類のcriteriaは1か所に定義し、JSONにもハッシュを記録する。
- 判定: `supports` / `contradicts` / `not_addressed` / `insufficient_context`
- 出力: 出典ファイル・行・原文・前後文、参照先・抜粋、確率、confidence、usage、時間、入力ハッシュ。自動修正・自動承認は行わない。
- 文脈は1組ごとに異なるため要求を分け、順次実行する。同じ状態への独立質問を無意味に複数要求へ分割しない。

## 固定評価データ

`scripts/fixtures/design-reference-evaluation.json` に24組、各分類6組を事前に用意した。採点、userId、SRS、教材の一次ソース、契約管理、Server loaderを題材にする。実際の文書を変えず、fixtureで主張を反転、存在する別の参照先へ差し替え、抜粋を不足させる。抜粋の元は `e0eefbade31fbcfe33faa6b12b2e743880fd7230`。fixtureのラベルと来歴は作成時点の暫定版として固定し、その後の人による確認は別の成果物に記録した。確認後もdatasetHashを変えない。

評価時に期待ラベル・ラベル理由をAPIへ送らない。`datasetHash` と `questionHash` を記録して比較条件を固定する。質問や抜粋を調整した場合は同じ評価と混同せず、新しい版で再評価する。24組は小さな動作検証用セットで、独立したholdout評価ではない。

## 正式な人手評価

同一の確認者が、Jevを画面に出さない直接確認24組、Jevの結果を表示した確認24組、最終ラベルの確認を順に行った。正式な画面のJSON出力日時は2026-10-18 01:08:29 JST。入力・結果のhash、24件のIDと順序、各組の時間の合計を照合した。比較は保存済みのAPI結果に対してオフラインで実行し、APIを再実行していない。

最終JSONの `grading-contradicts` だけが支持になっていたが、Jevあり確認時は矛盾だった。ユーザーに主張と根拠を示して確認し、最終判断「主張と矛盾する」を受けて集計に反映した。提出原文は `jev-human-timing-submitted.json` としてそのまま保存し、補正の理由・日時を付けた `jev-human-timing.json` と区別する。確定後の24ラベルはすべて事前の暫定ラベルと一致した。モデルや質問、fixture、API応答は変更していない。

先の画面操作確認で提出されたJSONは、ユーザーが操作確認用と明示しているため、時間・ラベルの正式評価から除外した。ただし操作確認でも同じ24組と判定画面に触れているため、正式評価にも先行露出による学習効果が残りうる。直接確認を先に行う順序効果、同じ主題を繰り返す効果、一人の確認者という条件も統制できていない。最終ラベルの確認時にはJevと暫定ラベルを既に見ており、独立した盲検アノテーションでもない。44.41%の時間差をJevだけの因果効果とは扱わない。時間は自己計測のアクティブ時間で、一時停止と非表示タブの時間を含まない。

## 確認できた境界と限界

キー未設定・参照切れ・予算超過・通信失敗・不正なChoiceを支持判定に変換しない。送信元は許可したポリシーファイルに限定し、リポジトリ外へのsymlinkも拒否する。クラウドのHTTP(S)プロキシ・NO_PROXY・CA trustを維持するため `undici` の `EnvHttpProxyAgent` を使う。Node 22.13以上を維持する。

抽出はリポジトリの限定Markdown書式が対象であり、任意のMarkdown構文は扱わない。主張は出典1行と前後1行を渡すため、複数行にまたがる条件や複数参照の帰属は曖昧になりうる。案内表を要確認にするので、読む文書の対応表そのものを自動的に保証する用途には使えない。大きな章は予算超過で未実行にし、本文を黙って落とさない。今回の24組は日本語の小規模な暫定評価であり、一般的な日本語精度やconfidenceの校正は検証できていない。

評価fixtureの `source.context` は全24組で「日本語の参照意味評価。実文書を編集せずfixture内で主張または参照先を改変。」という同じ説明文である。この文もAPIへ送っており、実文書で渡す前後の行とは条件が異なる。支持の6組は主張・参照先を改変していないため、この説明は各組の状態を正確に表しておらず、モデルに改変を疑わせる手がかりになりうる。クラスごとに異なるラベル漏えいではないものの、23/24という一致率を実運用へそのまま一般化できない。今回は条件を変更せず、同じhashでの人手比較と履歴を保つ。次の版では文脈を実際の前後文または空文字に変え、新しいdatasetHashで再評価する。

また、文脈不足の6組はすべて同じ主張「この境界では、それをその層だけで処理する。」を使っている。主張だけから分類できる可能性があり、抜粋が途中で切れていることを検出できるかは独立には測れていない。次の版では明確な主張と不足した抜粋を組み合わせた例、異なる表現、独立したholdoutを用意する。現在の6組を独立した多様な文脈不足事例として扱わない。

## 推奨と残対応

実API評価、人のラベル確認、時間比較はローカルで記録できた。判定候補の提示には使えた一方、モデルは文脈不足を1件取り違え、評価データの固定文脈や同じ主張の反復にも限界がある。このため手動の補助チェックとして試用を続け、次版では実運用に近い文脈、多様な文脈不足例、独立したholdout、別担当者または順序を入れ替えた時間比較を行うことを推奨する。誤支持0件は18組だけの結果であり、自動承認の根拠にはしない。

Issue #255の主分類は **未達・現在Issueに残す**。測定待ちは解消したが、残条件はユーザー承認後の既存PR #256への反映と、そのHEADでのCI確認である。マージは人間が判断する。移管先や置換PRは作らず、main反映後のclose候補は #255。#240/#242/#156は参照先で、親子フェーズとしては扱わない。次版への改善推奨は、今回の測定条件や完了条件を変更するものではない。
