フロントエンドアーキテクチャ

このページは docs/design.md の第8章・第9章を、実装時に参照しやすいようにフロー図とディレクトリ責務へ再構成した補助資料です。一次ソースは docs/design.md です。

設計文書 Markdown

基本方針

app は URL の入口

src/app は App Router の規約を置く場所です。URL、layout、metadata、error、route params を扱い、feature の loader に引き渡します。

features は画面価値の単位

features は lesson、quiz、review のような機能単位です。実行環境固有処理は client/・server/、両環境で使う処理は api/・mapper・ViewModel として責務別に近くへ置きます。

lib は横断インフラ

lib は API client、response helper、content index など feature 非依存の関数だけを置きます。画面都合の整形は置きません。

  • apps/web/src/app は routing と page 組み立てに限定し、ロジックは apps/web/src/features に寄せる。
  • 教材・問題は content/ を一次ソースとし、RSC / Server loader からビルド時バンドル済みデータを読む。
  • 解答ログ・SRS・due queue・各種集計（ダッシュボード統計・/domains の習得率・/analytics の集計）などの動的データだけを Hono API に集約し、フロントからは hc の型安全RPCで呼ぶ。集計系ページも RSC で、初回表示に必要な集計値を Server loader から読む（教材本文ページのみ API 不要）。
  • 演習・復習は 1 ルート内でクライアント状態遷移（intro → exercise → result）を持つ（別 URL に切らない）。初回データ （問題・解説、/review は due queue）は Server loader で ViewModel 化して props 渡しする。Client Component は画面フェーズ・現在問題・wrongOnly・キーボード操作を、Client hook は submitting・送信エラー・API 由来の解答結果を state に持つ。
  • web と API は別 Worker（design.md §3.1）。Server loader からは Service Binding （env.API）で内部呼び出し、Client hook からは API Worker の公開 URL で呼ぶ。どちらの経路でも hc<AppType> の型は同一。
  • 初回表示は Server loader で ViewModel 化して props 渡し、Client Component はその VM をそのまま描画に使う（state に複製しない）。Client hook は mutation と、それに伴う submitting・送信エラー・API 由来の結果だけを持つ。
  • due queue の再取得は Client 側で content join をやり直すのではなく、router.refresh() で Server Component を再実行し、Server loader が新しい VM を作り直す。
  • 正誤判定は API（サーバー）が権威。VM は選択肢と解説のみを持ち、正解 （answerIndex）を含めない。
  • cacheComponents は有効化済み。dynamic / dynamicParams の route segment config は併用できないため置かない。 PPR streaming の対象は / と /review のみで、後者では 静的シェルに ReviewQueueFallback を表示してから、queue 完了後に 非キャッシュの ReviewUserContent が整合性エラー・空キュー・ ReviewRunner を分岐してストリーミングする。
Cache Components / PPR 方針
due 件数・ダッシュボード統計・review queue は API が user_id を 権威的に注入する一方、web の共有キャッシュキーには含まれません。したがって 'use cache'・cacheLife・cacheTag・ revalidateTag は使わず、Suspense による分離だけを行います。解答後は router.refresh() で Server loader を再実行します。未実装の /domains と /analytics も、実装時に同じ静的シェルと 非キャッシュ動的領域の分離を適用しますが、PPR streaming 対象への追加は別途判断します。 /learn/... と /quiz/... は content 由来の prerender を維持し、 PPR streaming の対象外です（generateStaticParams と 'use cache' で全件を build 時に生成します）。
検証結果と残る制約
OpenNext #1130（production-only SyntaxError／Suspense 描画失敗）と #1225（Suspense streaming が完了せず Connection closed）は 未 close ですが、issue #93 の検証では本リポジトリの構成で再現しませんでした。 opennextjs-cloudflare preview で静的シェル → streaming 差し替え、hydration、 解答後に動的領域が再実行されること（共有キャッシュに乗らないこと）を確認済みです。 ただし現行 CI は next build のみで OpenNext preview のストリーミングを検知しません。 PPR の描画・streaming に関わる変更と、OpenNext / Next の更新時は手動 preview で再確認します。 詳細は design.md §12.8 を参照してください。
ディレクトリ名だけで実行場所は決まりません。apps/web/src/features/*/server は apps/web/src/app/**/page.tsx など Server Component から import されることでサーバー側で実行されます。誤 import 防止として import 'server-only' を置きます。
client/・server/ は実行環境の境界、components・hooks・loader は責務の境界です。両環境から使える endpoint アダプター・mapper・ViewModel はどちらにも複製せず feature 直下へ置きます。Client Component の入口には 'use client' を置きます。

依存方向

基本方向は app → features → components/ui・lib → packages/shared / 外部ライブラリ です。feature 内でも実行環境と責務を跨いだ近道を作りません。

  • app は feature の server と client/components だけを利用し、content・API adapter・mapper・hook を直接利用しない。
  • client/components は同 feature の client/hooks と ViewModel を利用し、 server・content loader・API client を直接利用しない。
  • client/hooks は Browser API client を生成して同 feature の API adapter に渡し、server・content loader・mapper・ViewModel を保持しない。
  • Server loader だけが content loader を利用し、取得・join・mapper 呼び出しを経て ViewModel を返す。
  • feature 間の再利用は features/shared の小さい純粋変換か、公開された component の props 契約を境界にする。他 feature の内部層を直接 import しない。

判断基準

迷った時は「どこから呼ばれるか」ではなく「何の責務か」で置き場所を決めます。

迷う処理 置き場所 理由
route params から lessonId を取り出す app/**/page.tsx App Router の URL 境界そのものだから。
lesson content を読み、LessonViewModel に変換する features/lesson/server lesson feature の初回データ形成だから。page に置くと page が厚くなる。
review queue DTO と content question を join する features/review/server + features/review/mapper.ts review 画面の表示要件に合わせた ViewModel 化だから。
client.review.queue.$get() を呼ぶ features/review/api Hono RPC の endpoint アダプターとして feature 単位に閉じるため。
res.ok チェックと res.json() lib/api.ts 全 endpoint で同じ横断処理だから。
ボタン、カード、入力欄などの汎用見た目 components/ui feature と無関係に再利用できる UI だから。
採用する考え方

app は薄い controller、features/*/server は Server 専用 loader、mapper は純粋変換として分ける。

避ける考え方

「page からしか呼ばないから page に全部書く」と判断する。これは URL 境界と機能ロジックを混ぜる原因になる。

ReviewViewModel.dueCount は content と join できた表示可能件数です。一方、 ダッシュボードの due 件数は永続化された due-state の生件数なので、解決不能な content ID が残る場合は大きくなり得ます。表示可能件数が 0 で後続 batch がある組み合わせは、 完了ではなく route の error 境界へ渡すデータ整合性エラーとして扱います。

クライアント更新処理

ユーザー操作後は Client hook から Hono API を呼び、正誤判定・D1への記録・SRS更新をすべてAPI側に閉じます（クライアントは selectedIndex を送るだけで、正解を保持しません）。

解答の反応時間（responseTimeMs）は Client Component が選択肢の表示開始時刻からの経過時間として計測し、submitAnswer の引数として Client hook へ渡す（design.md §8.5）。Client hook は時刻を計測せず、受け取った値をそのまま API へ転送する。

ディレクトリの役割

features/quiz/
├── client/
│   ├── components/       # Client Components・表示操作 state
│   └── hooks/            # Browser client・mutation・通信 state
├── server/
│   ├── components/       # Server Components（必要な場合のみ）
│   └── load-quiz.ts      # 初回取得・join・ViewModel 生成
├── api/                  # Server / Client 共用 endpoint アダプター
├── mapper.ts             # 環境非依存の純粋変換
└── view-model.ts         # Server / Client 間の表示契約
パス 役割 置かないもの
apps/web/src/app App Router の page / layout / error。Server loader を呼び、ViewModel を component に渡す薄い入口。 DTO変換、APIレスポンス処理、複雑なUI state。
apps/web/src/features/*/client/components feature 固有の表示と、画面フェーズ・現在問題・wrongOnly・キーボード操作などの表示操作 state。入口に 'use client' を置く。 Server loader、content loader、API client の直接利用、DTO変換。
apps/web/src/features/*/client/hooks Client 専用。Browser API client の生成、mutation と、それに伴う submitting・error・API 由来の結果 state を扱う。 初回取得の必須データ形成、ViewModel の複製保持、画面フェーズなどの表示操作 state、server の import。
apps/web/src/features/*/server Server loader と必要な Server Component。初回取得、content/API DTO の取得、join、mapper 呼び出し、ViewModel 生成。初回表示経路で content loader を利用できる唯一の feature 層。import 'server-only' で境界を強制する。 Client Component からの import、ブラウザ専用API。
apps/web/src/features/*/api hc の endpoint adapter。呼び出し側から ApiClient を受け取り、path・method・引数・共有 Zod による入出力検証・機能固有のエラーメッセージを持つ。 API client の生成、ViewModel 化、UI state、cookies/headers など環境専用処理。
apps/web/src/features/*/mapper.ts Content data / DTO を ViewModel へ変換する純粋関数。 fetch、DBアクセス、副作用。
apps/web/src/features/*/view-model.ts web 表示都合の型。page/component がそのまま使える形を定義する。 API契約の一次定義。DTO は packages/shared 由来。
apps/web/src/features/shared contentQuestionToQuizQuestion のような小さい純粋変換。 共通 ViewModel、loader、hook、feature 全体の抽象化。
apps/web/src/components/ui Button / Card / Badge / ProgressBar / TermWin / Keycap などの汎用UI。Tailwind ＋ Dev-Native Neo Flat × Terminal デザイントークン（--bg / --surface / --well / --border 等、design.md §8.7）を土台に集約する。 feature 固有ロジック、データ取得。
apps/web/src/components（root） 全画面共通のレイアウト shell・テーマ切替（dashboard-shell.tsx ・theme-toggle.tsx）。依存してよいのは components/ui・lib/cn・React のみ。 feature 内部層（server/client/api/mapper）、content、API への直接アクセス。
apps/web/src/lib/api.ts createServerApiClient（本番は Service Binding の fetch、dev は URL フォールバック）/ createBrowserApiClient（公開 URL）の Hono client 生成と、requestJson による res.ok・res.json() の共通処理。 endpoint 固有の path・method・引数・Zod 検証、ViewModel 変換。
apps/web/src/lib/content.ts ビルド時バンドル済み content の参照口。lesson と question index を提供する。 feature 固有 ViewModel への変換。

// apps/web/src/features/lesson/mapper.ts
import type { BundledLesson } from '@tsl/shared';
import type { LessonViewModel } from './view-model';

export function lessonContentToViewModel(content: BundledLesson): LessonViewModel {
  return {
    id: content.lessonId,
    title: content.title,
    markdownBody: content.body,
    questions: content.questions.map((question) => ({
      id: question.id,
      prompt: question.prompt,
      choices: question.choices,
    })),
  };
}

復習ページ: 初回は Server、操作後は Client

server loader + client hook 
// apps/web/src/features/review/api/review-api.ts
import { type ReviewQueueResponse, reviewQueueResponseSchema } from '@tsl/shared';
import { type ApiClient, requestJson } from '@/lib/api';

// requestJson の戻り値を共有 Zod で parse してから返す
export async function fetchReviewQueue(client: ApiClient): Promise<ReviewQueueResponse> {
  const response = await requestJson(
    () => client.review.queue.$get(),
    'Failed to fetch review queue',
  );
  return reviewQueueResponseSchema.parse(response);
}
// apps/web/src/features/review/server/load-review.ts
import 'server-only';

import { connection } from 'next/server';
import { cache } from 'react';

import { createServerApiClient } from '@/lib/api';
import { getBundledQuestions } from '@/lib/content';
import { fetchReviewQueue } from '../api/review-api';
import { reviewQueueToViewModel } from '../mapper';
import type { ReviewViewModel } from '../view-model';

// export しない。畳み込み前の loader を外から選べると、取り違えても型で気づけない
async function loadReview(now?: number): Promise<ReviewViewModel> {
  // Cache Components 下ではリクエスト時実行を宣言してからでないと、Cloudflare context の
  // 解決も現在時刻の読み取りもできない。Date.now() を既定引数で先に評価しないこと。
  await connection();

  const dto = await fetchReviewQueue(await createServerApiClient());
  return reviewQueueToViewModel(dto, getBundledQuestions(), now ?? Date.now()); // join はサーバー側のみ
}

// この feature の唯一の loader 入口。due バッジと本文が別々の <Suspense> 境界から
// 同じ queue を読むため、リクエスト内で1回に畳む（畳まないと件数と中身が食い違いうる）。
// React の cache() はリクエストスコープであり、user_id を含められない共有キャッシュではない。
export const loadReviewOnce = cache((): Promise<ReviewViewModel> => loadReview());

// apps/web/src/features/quiz/client/hooks/use-answer-submit.ts
'use client';

import type { AnswerRequest } from '@tsl/shared';
import { useCallback, useRef, useState } from 'react';
import { type ApiClient, createBrowserApiClient } from '@/lib/api';
import { submitAnswer as postAnswer } from '../../api/quiz-api';
import type { SubmittedAnswer } from '../../view-model';

// VM は保持しない。mutation と通信状態だけを扱う hook（Quiz / Review 共用）
export function useAnswerSubmit() {
  // 生成は初回送信まで遅らせる。render 時に作ると SSR・prerender でも評価され、
  // ブラウザ専用の設定（NEXT_PUBLIC_API_BASE_URL）が無い経路で throw する。
  const clientRef = useRef<ApiClient>(undefined);
  const [error, setError] = useState<string>();  // 表示用の文言。Error は持ち回さない
  const [results, setResults] = useState<Record<string, SubmittedAnswer>>({});
  const [submitting, setSubmitting] = useState(false);
  const submittingRef = useRef(false);

  // responseTimeMs は Client Component が計測して input に含める（§8.5）。hook 側では計測しない
  const submitAnswer = useCallback(async (input: AnswerRequest) => {
    if (submittingRef.current) return;
    submittingRef.current = true;
    setSubmitting(true);
    setError(undefined);
    try {
      clientRef.current ??= createBrowserApiClient();
      const response = await postAnswer(clientRef.current, input);
      // API の採点結果に選択肢を足して SubmittedAnswer にする。選択肢のロックと
      // 結果サマリが「どれを選んだか」を必要とするため。
      setResults((prev) => ({
        ...prev,
        [input.questionId]: { ...response, selectedIndex: input.selectedIndex },
      }));
    } catch (caughtError) {
      setError(caughtError instanceof Error ? caughtError.message : '解答の送信に失敗しました。');
    } finally {
      submittingRef.current = false;
      setSubmitting(false);
    }
  }, []);

  const resetAnswers = useCallback(() => {
    setError(undefined);
    setResults({});
  }, []);

  return { error, resetAnswers, results, submitAnswer, submitting };
}
// apps/web/src/features/review/client/components/review-runner.tsx
'use client';

import { useRouter } from 'next/navigation';
import { useAnswerSubmit } from '../hooks/use-answer-submit';
import type { ReviewViewModel } from '../../view-model';

type Props = {
  viewModel: ReviewViewModel;
};

export function ReviewRunner({ viewModel }: Props) {
  const router = useRouter();
  const { results, error, submitting, submitAnswer, resetAnswers } = useAnswerSubmit();

  const handleAllAnswered = () => {
    resetAnswers();
    router.refresh(); // Server loader を再実行し、次の due queue を props で受け直す
  };

  if (error) {
    return (
      <ErrorDisplay
        error={error}
        retry={() => {
          resetAnswers();
          router.refresh();
        }}
      />
    );
  }

  return (
    <QuizRenderer
      viewModel={viewModel}
      results={results}
      submitting={submitting}
      onAnswer={submitAnswer}
      onAttemptStart={resetAnswers}
      onWrongOnlyStart={resetAnswers}
      onComplete={handleAllAnswered}
    />
  );
}

避ける例: page に ViewModel 化を直接書く

責務が混ざる例 
// apps/web/src/app/review/page.tsx
// 避ける: page が API DTO、content join、sort、ViewModel 形状を知っている。
export default async function ReviewPage() {
  const client = await createServerApiClient();
  const res = await client.review.queue.$get();
  const dto = await res.json();
  const questions = getBundledQuestions();

  const viewModel = {
    items: dto.items.map((item) => ({
      ...questions[item.questionId],
      dueAt: item.dueAt,
      stability: item.stability,
    })),
  };

  return <ReviewRunner viewModel={viewModel} />;
}
この例では page が Hono RPC、レスポンス処理、content join、ViewModel 形状をすべて知っています。変更影響が page に漏れるため、features/review/server と features/review/mapper.ts へ分けます。

API層との境界

apps/api/src/
├── routes/       # Hono route。HTTP契約と zValidator
├── services/     # ユースケース。SRS更新などの処理
└── dal/          # Drizzle / D1 への永続化アクセス

apps/web 側では _DAL / dal を置きません。DB に直接触る責務は apps/api 側に閉じ、フロントは Hono RPC wrapper 経由で DTO を受け取ります。

Worker 構成と接続（design.md §3.1・§8.4）

apps/web（OpenNext）と apps/api（Hono）は 別 Worker としてデプロイします。Next.js の Route Handler 上に Hono を載せる同居構成は採用しません（wrangler 設定の所有権・デプロイ独立性・§8.3 キャッシュ方針の前提を維持するため）。呼び出し元によって経路が変わりますが、 hc<AppType> の型安全RPCは両経路で同一です。

Server loader は Service Binding による内部呼び出し（公衆インターネット非経由・CORS 不要）、Client hook は公開 URL（当面は cors() で許可、将来はルート割当で同一オリジン化）です。

// apps/web/src/lib/api.ts
import { createClient } from '@tsl/api/client';

// Server loader 用: 本番は Service Binding 必須、ローカルのみ URL へフォールバック
export async function createServerApiClient(): Promise<ApiClient> {
  const isLocalRuntime = process.env.NODE_ENV !== 'production';

  try {
    const { getCloudflareContext } = await import('@opennextjs/cloudflare');
    const { env } = await getCloudflareContext({ async: true });
    if (env.API) {
      // ホスト名はダミー（Service Binding はパスのみ使用）
      return createClient('https://api.internal', {
        fetch: env.API.fetch.bind(env.API),
      });
    }
    if (!isLocalRuntime) throw new Error('Cloudflare API service binding (API) is not configured.');
  } catch (error) {
    if (!isLocalRuntime) throw error; // 本番は fail-fast
  }

  return createClient(process.env.API_BASE_URL ?? 'http://localhost:8787');
}

// Client hook 用: env から解決した公開 baseURL。生成は初回送信まで遅らせる
// （render 時に呼ぶと prerender でも評価され、未設定時に throw する）。
export function createBrowserApiClient(): ApiClient {
  const apiBaseUrl = process.env.NEXT_PUBLIC_API_BASE_URL;

  if (!apiBaseUrl && process.env.NODE_ENV === 'production') {
    throw new Error('NEXT_PUBLIC_API_BASE_URL is required in production');
  }

  return createClient(apiBaseUrl ?? 'http://localhost:8787');
}
web 側の wrangler 設定に "services": [{ "binding": "API", "service": "<API Worker 名>" }] を宣言します。apps/api/src/client.ts のファクトリは hc の第2引数（fetch オプション等）を受け渡せる形に拡張します。
