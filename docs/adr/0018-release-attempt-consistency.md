# 0018: 変更処理の開始から成功までを記録し、省略判定を環境の状態に合わせる

- 状態: Accepted
- 日付: 2026-11-06
- 関連: Issue #286、ADR-0017 を補完する

## 背景

最後の成功ソースと候補が同じでも、実環境が成功時の状態とは限らない。先行リリースの適用中に古い成功記録で省略を決めると、その後に先行リリースが成功しても計画を見直せない。また、失敗したリリースが D1 を同期した後でソースを成功版へ戻すと、ソース差分がなくなり、誤った正答データが残る。

毎回両 Worker をビルドする方法は変更範囲に応じて省略する目的に反する。すべてのドキュメント更新で D1 を同期する方法も、配備の必要がない更新に変更権限を渡すことになる。代わりに、計画の順序と未完了の変更処理を記録して判断する。

## 決定

1. 同一環境の通常リリースは、計画・準備・適用・成功記録までを同じ排他制御の中で行う。Worker のロールバックも同じ排他を使う。先行適用が終わる前に、後続が古い成功記録から省略を確定しない。
2. 変更前の検査が通った後、D1 または Worker を変更する前に GitHub Deployment へ開始記録を保存する。開始記録を保存できなければ変更しない。ロールバックでも Worker を変更する前に開始を記録する。
3. 直近の成功・ロールバック記録より新しい開始記録があれば、環境の状態は比較不能とする。失敗・中断・応答切断でも開始記録を残し、次回は両 Worker の準備・migration/content sync・配備・検査を実行する。ソースが過去の成功版と一致しても省略しない。
4. 全段階が完了して成功記録を保存した場合だけ、その開始記録より新しい成功記録を比較元にできる。検証環境に未完了の開始記録がある間、本番昇格の証跡にも使わない。

## 境界

- 開始記録は成功の証明ではない。性能試験・実 version・ソース照合など ADR-0017 の検査は維持する。
- 開始前の検査やビルドだけの失敗では遠隔状態を変更していないため、開始記録を作らない。開始後に遠隔変更を行っていない場合も、安全側に倒して次回は全体を反映する。
- 正常な成功記録があり、未完了の変更処理も配備対象のソース差分もなければ、従来どおりビルド・配備・D1 同期を省略する。開始記録は環境ごとに扱う。
- GitHub Deployment を使う通常経路とロールバックが対象。記録を経由しない外部の手動変更は、手動 Deploy で全体を反映する。
