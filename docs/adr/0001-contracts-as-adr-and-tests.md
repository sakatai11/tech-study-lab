# 0001: 設計契約を ADR とテストで管理する

- 状態: Accepted
- 日付: 2026-10-13
- 関連: Issue #240

## 背景

`docs/design.md` を仕様駆動開発の一次ソースとし、仕様を変えるときは文書を先に更新してから実装してきた。プロダクトが成熟するにつれて、次の問題が出た。

- ほぼすべての PR で `design.md` を更新していた。その多くは実装を文書へ書き写すだけで、判断の根拠としての価値が更新の手間に見合わなくなった。
- 撤去済みの機能への言及、移行期の手順、過去の経緯が本文に残り、AI が古い情報を現在の契約と取り違えるおそれが出た。
- 現在の構造は Knowledge Graph が、型の契約は共有 Zod が持つようになり、`design.md` の現状記述はそれらと二重管理になっていた。

一方で、`design.md` を完全に廃止すると、「なぜそうするか」と「どこまで適用するか」がどこにも残らない。その場合、現在の実装がそのまま正解とみなされ、バグと仕様を区別できなくなる。

## 決定

1. 不変条件はテストで機械的に検証する。
2. テストで表せない理由と境界だけを `docs/adr/` に ADR として残す。ADR は採用後に書き換えず、判断を変えるときは新しい ADR で置き換える。
3. ADR を作るのは、契約を新設・変更する Issue だけとする。UI の文言や表示の細部は、コードとテストだけで変更する。
4. 契約の優先順は ADR → 共有 Zod 契約 → テスト → 実装 とする。
5. `docs/design.md` は段階的に縮退させ、最終的にプロダクト方針・依存方向・ADR 索引だけを持つ。移行が済むまでは、未移行の節を引き続き設計契約として扱う。

## 境界

- 対象は、AI や人がコードを読んで逆の判断をしうる設計判断（権威の所在、信用境界、データの整合性、セキュリティ、運用順序）である。
- 現在のファイル配置・型・関数シグネチャは ADR に書かない。コード・共有 Zod・Knowledge Graph を一次ソースとする。
- 過去の調査・比較・検証結果は `docs/investigations/` に置く。ADR には、採用した判断とその理由だけを書く。
- 運用ルールの詳細は [README](./README.md) が持つ。
