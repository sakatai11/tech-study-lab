# 0010: リリースはスキーマ → データ → API → 画面の順に適用する

- 状態: Superseded by [ADR-0016](./0016-performance-gated-promotion.md)
- 日付: 2026-10-14
- 関連: Issue #242（`docs/design.md` の旧 12.4 節・旧 12.9 節から移行）

## 背景

リリースでは、D1 のマイグレーション、content の同期、API Worker、Web Worker を更新する。順序を誤ると、更新の途中で稼働中の旧バージョンが新しいスキーマやデータと食い違って壊れる。途中で失敗したまま後続を進めると、壊れた状態が広がる。

## 決定

1. リリースは「マイグレーション → content の同期 → API → 画面（Web）」の順に適用する。各段階の完了時点で、稼働中の旧バージョンが壊れないことを前提にする（マイグレーションは後方互換の追加が中心。ADR-0011）。
2. 各段階の成功を確かめてから次へ進む。どの段階で失敗しても、そこで停止して後続を実行しない。
3. CI のリリースは、事前検査、マイグレーション、同期、API、API の確認、Web、smoke test、成功の記録の順に進め、同じ規則に従う。手動での運用も同じ順序に従う。

## 境界

- 本番 Web を最初に Vinext へ切り替えるときは、API・D1 の契約が変わらないため、Web の段階だけを実行する（Issue #221）。
- 復旧（ロールバック）は Worker の version を指定して行う別の手順であり、D1 の状態は戻らない。
- 具体的なコマンド、環境設定、承認の扱いは運用の手順が扱う。

## 検証

- [deployment.test.mjs](../../scripts/deployment.test.mjs): リリースの各段階を決められた順序で実行し、どの段階で失敗しても後続を実行しない
- [deployment-cli.test.mjs](../../scripts/deployment-cli.test.mjs): 実際の適用 CLI が準備済みの成果物を順に反映し、不正なリリースを変更の前に拒否する
