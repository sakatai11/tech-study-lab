## 評価

初期実装とレビュー修正後を区別して評価する。両実行で typecheck / lint（dependency-cruiser含む）/ test / build を実行し、未実行・失敗を合格へ読み替えない。可能な範囲でローカルD1主要経路と画面を確認する。

レビューは同じ受け入れ条件、`.ai/review-guidelines.md` の重要度・プロファイルで行う。条件名は可能な限り伏せるがPoCファイルから推測可能なため完全な盲検とは主張しない。必須の別モデルレビューは実際の差分を確定してから規約に従う。

| 指標 | 集計方法 |
| --- | --- |
| 受け入れ条件 | 共通仕様の項目ごとに達成・未達・未確認 |
| 品質ゲート | 実コマンド・終了コード・テスト件数 |
| レビュー | 初期指摘と修正後のmust-fix / should-fix / nit、修正周回 |
| 差分 | 各条件の実装開始点からのファイル数・追加/削除行数（品質そのものとはしない） |
| トークン | CLI turn.completed.usage を集計。inputはcachedを含み、total=input+output。reasoningはoutput内訳として別表示し二重加算しない |
| 経過時間 | 起動から終了まで。待機・依存インストール・事前準備・レビューは別表示 |
| 補助指標 | command execution回数、検索／読み取りコマンド数。自動計測できない読取行数は未取得 |

CLI最小疎通確認は input=21,291、cached=0、output=5。機能実装費用に含めず準備費用として記録する。Astraタスク／補助エージェントの完全な課金トークンが取得不能なら未取得とし、goalツールの会話トークンをCLI課金トークンと同一視しない。アカウント全体の使用率から換算しない。

PoC checkは両条件の最終コードに対して評価者が実行する。PoCなしの実装中にはこの情報を渡さない。PoC構築・データ追従の費用は分離し、実測できる場合だけ回収回数を計算する。

## 制約と交絡要因

親タスクは旧 #33 作業の状態確認で履歴に触れている。各Sol実装にはその履歴・コード・調査メモを渡さず、PoC構築担当にも旧実装を読ませない。OS・依存キャッシュ・モデル揺らぎ・実行順・CLI共通コンテキストの影響は残る。PoCデータの追加だけでなく参照とチェックを含む運用全体の比較であり、表現形式単独の因果効果は分離しない。

恒久採用、実装の選択、追加反復の必要性を最終レポートで示す。マージは人間の判断とする。
