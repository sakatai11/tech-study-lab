Authentication / Authorization / Trust Boundary

認証を「入口」ではなく、信頼経路として設計する

tech-study-lab の単一ユーザーMVPでは、Cloudflare Accessが利用者を認証し、API WorkerがJWTを再検証します。Server loaderは公開HTTPを通らず、privateなService Bindingを使います。この文書は、その責務分担と通信順序を1枚で追えるようにまとめたものです。

01 / Contract

この方式が守る4つの原則

「ログイン済みらしい」という曖昧な状態を信用せず、経路ごとに誰が何を保証するかを固定します。

利用者の認証はAccess

アプリ独自のログインフォームやパスワードを持ちません。Cloudflare Accessの認証画面とPolicyで、許可された利用者だけを保護対象へ通します。

公開トップはユーザーデータを読まない

/は未認証で表示できる説明ページです。ログインCTAは/homeへ進み、必要ならAccessが認証画面へ転送します。

APIはAccessヘッダーを鵜呑みにしない

API Worker自身がJWTの署名・issuer・audienceを検証します。検証成功後にだけuserContextが固定ユーザーを注入します。

内部通信は公開HTTPと分離する

Web WorkerのServer loaderはnamed InternalApi Service Bindingを使用します。内部経路を偽装可能なHTTPヘッダーで表現しません。

02 / Trust map

4層の信頼境界

認証情報は各層を自由に通過しません。Cloudflare edgeの認証、Web Workerの画面責務、API Workerの認可、D1のユーザーデータを分離します。

EDGE.01

Cloudflare Access

利用者を認証し、Policyを評価して、認証済みリクエストへAccess JWTを付与します。

WEB.02

Web Worker

公開トップと認証後画面を描画し、Server loaderからprivate bindingを呼びます。

API.03

API Worker

公開経路ではJWTを検証し、内部経路ではnamed entrypointの能力を信頼します。

DATA.04

D1

固定user_idに紐づく解答ログ、SRS状態、閲覧ログを保持します。

04 / Route policy

経路ごとの認証ルール

「アプリ全体を一律に保護」ではなく、公開トップ、認証後画面、公開API、内部API、health、ローカル開発を明示的に分けます。

経路 分類 認証・認可 ユーザーデータ 状態
GET / PUBLIC 不要 取得しない Issue #127で変更予定
GET /home・/review等 ACCESS Cloudflare Access session + Policy Server loaderから取得 /homeはIssue #127
POST /answers・/lesson-views ACCESS + JWT edge認証 + API WorkerでJWT検証 読み書きあり PR #126
GET /dashboard/due-count等 INTERNAL named Service Binding InternalApi 読み取りあり PR #126
GET /health PUBLIC 不要 なし 公開維持
localhost / loopback LOCAL ONLY Access設定が両方ない場合だけbypass ローカルD1 設定済み・設定不足・非loopbackではfail closed

05 / JWT verification

Access JWTを検証してからuserContextへ渡す

API Workerの検証は4段階です。どれか1つでも失敗したら、固定ユーザーIDを作らずに終了します。

設定

ACCESS_ISSUERとACCESS_AUDIENCEが揃っているか確認。

トークン

Cf-Access-Jwt-Assertionが存在するか確認。cookie本文は検証元にしない。

署名

信頼するissuerから導出したAccess JWKSでJWT署名を検証。

claims

issuerを完全一致、audienceを対象ApplicationのAUDと照合。

単一ユーザーの保証はAccess Policy側にもある

APIはJWTのidentity claimを複数ユーザーIDへ変換しません。許可主体を単一ユーザーに絞る責務はIssue #35で設定するCloudflare Access Policyが持ち、APIは認証成功後に固定user-local-001を注入します。

06 / CORS & cookies

Access edgeとWorker内CORSは別の責務

Cloudflare Access edge

  • 保護対象のweb/API hostnameを定義する
  • 未認証利用者へ認証画面を返す
  • preflightをWorkerへ転送するか同等の応答を返す
  • credentialed cookieが本番hostnameで送信できる構成にする

API Worker CORS

  • WEB_ORIGINと完全一致するoriginだけを許可
  • credentials: trueを返す
  • GET / POST / OPTIONSとContent-Typeを許可
  • Workerへ届いたOPTIONSは204で終了し、D1へ到達させない
推奨: webとAPIを同一siteに寄せる

cross-site cookie制約を減らすため、本番では同一zoneの明示的なhostnameまたはpath routingを優先します。具体的なhostname・cookie・preflightの組み合わせはIssue #35で実機確認します。

08 / Decisions

採用した方式と採用しなかった方式

採用: Access + API JWT検証 + Service Binding

利用者認証、originでの検証、内部Worker通信を別々の仕組みで保証します。アプリ独自の認証UIを持たず、公開HTTPと内部経路を明確に分離できます。

不採用: Web proxyだけでAPIを隠す

proxy自体が公開HTTPならcurlやbotも呼べます。Origin・Referer・User-Agentやブラウザ配布済みsecretは利用者の真正性を保証しません。Accessを併用すると不要な中継層になります。

09 / Failure behavior

失敗した場所から原因を切り分ける

観測される状態 主な原因 データ保護 確認箇所
Access認証画面へredirect sessionなし・期限切れ・Policy未許可 Workerへ未到達 Access Application / Policy
CORS error / preflight失敗 Access edgeまたはWEB_ORIGIN不一致 本リクエスト未実行 Access CORS設定・Worker CORS
固定401 JSON Access vars・token・署名・issuer・audience不正 userContextとD1へ未到達 API Worker vars・JWT検証
Server loaderがfail-fast 本番Service Binding未設定 公開URLへfallbackしない Web Worker API binding
localhostのみ認証なしで成功 Access設定が両方未設定の明示的なloopback開発経路 ローカルD1のみ request URL hostname
