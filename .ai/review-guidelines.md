# レビュー規約

このリポジトリでコードレビューを行うすべての主体（人間・`reviewer` エージェント・別モデルCLIの結果を判定するオーケストレーター）が従う共通規約。**レビュー範囲・レビュー観点・重要度・ADR と design.md の読み方の単一ソース**であり、他の文書はここを参照して再掲しない。

## レビュー範囲

レビューの目的は、差分の周辺で見つかるすべての問題を当該 issue へ取り込むことではない。依頼で指定された範囲に対して、差分が正しく安全に受け入れ条件を満たすかを判断することである。

レビューの依頼には、少なくとも次の項目を明示する。

- `targetFeature`: 今回変更する対象機能・振る舞い
- `inScopeFiles`: 今回の修正対象として合意したファイルまたはパス。関連を調べるために読むだけのファイルは含めない
- `acceptanceCriteria`: 今回の受け入れ条件
- `outOfScopePolicy`: 範囲外の問題は「別issue候補（範囲外）」または「確認事項」として報告し、当該 issue の修正ループと判定件数には含めないこと
- `committedRange`: 今回レビューするコミット済み差分の範囲

依頼の項目が欠けている、または相互に矛盾していて範囲を決められない場合、レビュアーは推測で補完せず、レビューを `error` として不足項目を報告する。`committedRange` が実際のコミット済み差分と一致しない場合も同様に `error` とする。

`content-new`がコミット前の教材を確認する場合だけ`reviewStage: content-draft`を使う。この段階は上記の`committedRange`に代えて、変更済みまたは新規の`content/**`だけを列挙した`draftPaths`を必須とし、`inScopeFiles`を`draftPaths`と一致させる。レビュアーは`git status --short -- <draftPaths>`、追跡済みファイルの`git diff -- <draftPaths>`、各教材ファイルの全文を読み取り専用で確認する。`content-draft`はコミット前の教材チェックであり、コミット済み差分のレビューの代わりにはならない。`draftPaths`外の未コミット変更を理由に停止せず、範囲へ含めない。

### 範囲判定

各候補を、重要度を付ける前に次のいずれかへ分類する。

1. **対象範囲内**: `targetFeature` または `acceptanceCriteria` に直接関係し、かつ指摘箇所が `inScopeFiles` に含まれる、今回の変更として修正可能な問題。`inScopeFiles` に含まれることだけでは対象範囲内にしない。must-fix / should-fix / nit の対象にする。
2. **今回差分が起こした範囲外機能の回帰**: 対象機能の外側であっても、今回の committed range が既存機能を実際に壊したと根拠を示せる問題。今回の変更の回帰なので対象範囲内として扱い、重要度を付ける。
3. **別issue候補（範囲外）**: 問題は妥当だが、今回差分が原因ではなく、対象機能・対象ファイル・受け入れ条件に直接関係しない問題。must-fix / should-fix / nit に変換せず、理由・影響・切り出し案を報告する。
4. **確認事項**: 根拠不足、または範囲内か範囲外かを確定できない問題。判定に数えず、確認したい事実を明記する。

差分の周辺コード、呼び出し元、設計文書、テストを読むことは推奨する。ただし、レビュー対象の外側を読んで問題を発見したこと自体は、当該 issue の修正対象にする根拠にならない。

### 重大問題の例外

- 今回差分がセキュリティ問題、データ破壊、または範囲外機能の明白な回帰を新たに起こす場合は、上記「今回差分が起こした範囲外機能の回帰」として握り潰さず、must-fix を含む適切な重要度で当該 issue の判定に含める。
- 今回差分が原因ではない範囲外のセキュリティ問題・データ破壊リスクは、自動的に当該 issue の修正対象へ広げない。「別issue候補（範囲外）」へ記録し、悪用中・即時のデータ損失など緊急性がある場合だけユーザー判断へエスカレーションする。ユーザーが明示的に範囲を変更するまでは修正ループと判定件数に含めない。

## 読む文書（ADR と設計・規約の対応）

設計契約は [ADR](../docs/adr/README.md) とテストが持つ（ADR-0001）。レビュー時は、**変更ファイルの領域に関係する ADR** を読んでから差分を判断する。層と依存方向・データフローは `docs/design.md`、画面・教材・運用の規約は各規約文書で確認する。

| 変更ファイル | 読む ADR | 読む設計・規約 |
|---|---|---|
| `apps/web/**` | 出題・解答は ADR-0002、API の呼び出しと書き込みは ADR-0012、認証後の画面の描画とキャッシュは ADR-0013 | design.md §4.2・§5 / [デザインシステムと画面の規約](../docs/design-system.md) |
| `apps/api/**` | ADR-0002〜ADR-0009・ADR-0014 のうち関係するもの（content 同期は ADR-0006、学習分析は ADR-0007、最近のアクティビティは ADR-0014、公開 entrypoint と Access は ADR-0008、解答の書き込みは ADR-0009） | design.md §4.3・§5.7・§5.8 |
| `packages/shared/**` | API スキーマは ADR-0002 / ADR-0003 / ADR-0007 / ADR-0014、SRS は ADR-0005、content のスキーマは ADR-0006 | design.md §5.1・§5.8 |
| `content/**` | ADR-0006 | [コンテンツ規約](../docs/content-guidelines.md) |
| テストファイル | テスト名に `[ADR-NNNN]` がある場合はその ADR | [テストルール](rules/testing.md) |
| ビルド・デプロイ・CI 設定 | ADR-0010（リリースの順序）、ADR-0011（マイグレーション）、ADR-0012・ADR-0013（Worker 構成とキャッシュ） | [環境・デプロイ運用](../docs/deployment.md) |

ADR の一覧は [`docs/adr/README.md`](../docs/adr/README.md) の索引にある。上の表は代表的な対応を示すもので、索引から変更内容に関係する ADR を選ぶ。複数領域にまたがる場合は該当する ADR と文書をすべて読む。`.ai/rules/*.md` が指す章番号（例: 「design.md 5.3」）も併せて参照する。

## Jev設計参照チェック

通常のAIレビュー依頼でも、レビューの実行責任者が次の条件を判定する。Jevは文書間の意味対応の補助であり、コードレビュー・独立レビュー・既存ゲート・人間の判断を置き換えない。新しい必須承認ゲートにはしない。CIや編集hookからAPIを呼ばない。

### 対象選択とdry-run

1. `committedRange` の両端のcommitを確定する。3点差分ならmerge-baseをbaseにする。`pnpm --silent design-ref:review --base <baseCommit> --head <headCommit> --dry-run` のJSONを読む。コマンドはこの2点間の差分を使い、renameは旧パスの削除と新パスの追加として扱う。参照元・参照先の作業コピーはheadと一致させる。不一致は `review_context_dirty` で停止する。無関係な作業ファイルは対象にしない。教材draftだけのレビューは対象外として記録する。
2. 参照元 `AGENTS.md` / `.ai/review-guidelines.md` / `.ai/rules/*.md` の変更では、そのファイルを明示選択する。参照先 `docs/design.md` / `docs/adr/` の番号付きADRだけの変更でも、現在の参照を逆引きして影響する参照元を選ぶ。章内の微小差分を見落とさないよう参照先は**文書単位**で保守的に判定し、選んだ参照元の全参照を候補にする。対象文書変更時の未解決参照も残す。対象を自動で全ポリシーへ広げたり、Graphで代用したりしない。
3. JSONの `sources`（明示パスと選択理由）、`deletedSources`、`rows`（参照元の行・前後文、参照先の抜粋・位置、要確認理由）、`endpoint`、`model`、`questionHash`、`maxRequests`、`planHash` を確認する。通常コードだけの差分、参照元がない場合は `no_affected_sources`、参照のない参照元だけなら `no_references_in_selected_sources` として未実施を報告する。削除した参照元に対するAPI判定は行わない。許可外の実パス・symlinkは読み取り時に拒否される。

### 外部送信の許可

- キー・ネットワークの利用可能性、Issueの実装依頼、過去のAPI実行は、今回の外部送信への同意ではない。本文の読み取りが許されても外部送信まで許されたとは解釈しない。
- ユーザーはdry-runの特定の `planHash` を今回限りで許可できる。または、**今回のレビュー範囲・送信可能な参照元パス・参照先パス・送信内容（行と前後文、参照先抜粋と出典）・送信先・モデル／質問版・要求上限**を指定して事前許可できる。例: 「このPRのレビュー中、`.ai/rules/web.md` の参照行と前後文、および参照する `docs/design.md` とADRの抜粋・出典をTypeSafeの固定endpointへ、現行固定モデル／質問版、最大30要求で送ることを許可」。この許可は当該レビューだけに適用し、恒久ルールに書き戻さない。
- 実行責任者はセッションの同意と適用される権限を確認する。事前許可が候補をすべて覆う場合は追加確認せず実行する。未承認・範囲外の参照元／参照先・上限増加・送信先や質問の変更には追加確認が必要。承認済みの一部に合わせて黙って候補を削ったり広げたりせず、実行を保留し、候補と不足条件を示す。今回限りの許可や別レビューの結果を再利用しない。
- 許可されたdry-runの `planHash` を `--execute --approved-plan <planHash>` に渡す。実行時に再収集し、hashが変われば `approved_plan_mismatch` で送信を止める。再dry-runして同意範囲を再確認する。hashは内容の固定であり、同意の証明ではない。実行責任者はAIの自己判断で許可を捏造しない。
- 1つのレビューでAPIを呼ぶ担当は1人にし、他のレビュアーへ同意の範囲・commit範囲・planHash・JSON結果を `designReferenceReview` として渡す。同じ候補への重複送信はしない。受け手は範囲とhashを確認し、結果を読む。古い結果や欠落を成功と扱わない。読み取り専用サブエージェントが実行権限を持たない場合は実行責任者へ未実施を返す。

### 起動と失敗時の扱い

- `pnpm design-ref:review` と `pnpm design-ref:check` は `.env.local` を自動読み込みしない。ユーザーが起動前に用意した `TYPESAFE_API_KEY` の環境変数・クラウドのsecret bindingを継承する。キーを表示・コマンド引数・ログへ記録しない。存在確認は値を出力せず行う。`.env.local` を子プロセスから読むことも機密ファイルの読み取りであり、Claudeのdenyや適用中の権限を迂回しない。キー設定のためにAIがファイルを開いたり `source` / `--env-file` を使ったりしない。
- `dependency_missing`: `undici` 等の依存が未導入。許可された環境で `pnpm install --frozen-lockfile` 後に再dry-runする。dry-runとキーなしの確認は依存なしでも動く。
- `missing_api_key`: 未実施。利用者による環境変数の設定が必要。`network_error` / `request_timeout`: 通信・proxy・CA・許可ホストを確認する。`http_<status>`: API側の認証・制限・障害を確認する。`invalid_json` / `invalid_response`: 応答形式不正であり判定に使わない。レスポンス本文・認証ヘッダー・生の例外をログへ出さない。
- `request_budget_exhausted` / `context_budget_exceeded`: 未実施。上限の引き上げは同意範囲を再確認し、抜粋を黙って切り詰めない。既定30要求・最大100要求、1要求30秒・24,000 bytes以内。最初のエラーで後続を `stopped_after_error` にし、自動リトライしない。再実行が必要なら原因を解消し、残予算と同意を確認して明示的に1回ずつ行う。
- `approval_required` / `approved_plan_mismatch` / `review_context_dirty` / パス拒否も未実施理由として残す。未実施・失敗は正常判定や承認ではない。Jevが実行できなくても通常のコードレビューを続け、補助チェックの未実施を明示する。

### 結果のレビューへの対応付け

終了コードだけで判断せずJSONの全 `rows` と `findings` を読む。`source.file:line`、`target.file` と章／行、判定、要確認理由をレビュー結果へ対応付ける。`contradicts` / `not_addressed` / `insufficient_context` は元文書を確認する**候補**であり、自動修正・自動承認しない。`supports`・confidenceも正しさの保証ではない。`needs_confirmation`（案内表・コード例・文書全体参照など）は送信せず、`local_error`（未解決参照）はローカルで確認する。

報告には、実行／対象外／未承認／失敗の別、commit範囲、選択ファイル、planHash、要求件数・残った未実施、上記の対応表と元文書の確認結果を含める。Jev単体の候補をmust-fixへ変換せず、本規約の範囲判定・重要度に従う。`completed` は送信可能な参照の処理完了で、未送信の `needs_confirmation` は引き続き手動確認が必要である。

## レビュー観点

次の5つを扱う。**優先順は担当するレビュープロファイルによって変わる**（次節）。

1. **契約準拠**: 関連 ADR の「決定」と「境界」、`docs/design.md` の依存方向とデータフロー、受け入れ条件に沿っているか。契約を新設・変更する差分では、先に ADR が作られているか、ADR を検証するテストが `[ADR-NNNN]` 付きで存在するか。
2. **ガードレール違反**: `any` の使用、`packages/shared` 外での型・スキーマの二重定義、Zod バリデーションの欠落、SRS ロジックと副作用の混在、教材本文の D1 直接書き込み。
3. **正確性**: バグ、ロジック誤り、エッジケース（null / 空配列 / 境界値）、非同期処理の誤り。
4. **セキュリティ**: 入力検証漏れ、SQL インジェクション、ユーザー分離の欠落。
5. **テスト**: 新規ロジックにテストがあるか。テストが実質を検証しているか。

## レビュープロファイル

複数のレビュアーを並列に走らせるとき、全員が同じ優先順で読むと同じ見落とし方をする。**プロファイルで優先順を変えて補完させる。** 各レビュアーは自分に割り当てられたプロファイル1つだけを参照する。

### `accuracy-first`（正確性優先）

担当: `reviewer`、および GitHub App 方式で並列実行する1件目の `reviewer`。

優先順: **正確性 → セキュリティ → 契約準拠 → ガードレール違反 → テスト**

バグ・ロジック誤り・エッジケースを最優先で探す。契約準拠も見るが、正確性の検証を削ってまで ADR や章を読み込まない。

### `spec-compliance-first`（契約準拠優先）

担当: 別モデルCLIのレビュー（依頼時にこのプロファイルを指定し、結果はオーケストレーターが判定する）、および GitHub App 方式で並列実行する2件目の `reviewer`。

優先順: **契約準拠 → ガードレール違反 → 正確性 → セキュリティ → テスト**

関連 ADR の「決定」と「境界」、`docs/design.md` の依存方向とデータフロー、受け入れ条件への適合を最優先で検証する。ADR の境界の内側で決定に反する実装は、それ単体でバグがなくても must-fix として扱う。境界の外側への適用拡大や、ADR を作らずに契約を変える差分も指摘する。

## 重要度

- **must-fix**: バグ・契約違反・受け入れ条件の未達・セキュリティ問題・データ破壊の可能性。確信がある場合のみ付ける。
- **should-fix**: ガードレール違反・保守性の問題・エラーハンドリング不足。
- **nit**: スタイル・命名・コメントなど好みの範疇。fix ループには回さない。

## 報告のしかた

推測ベースの指摘はしない。確認できなかった懸念は「確認事項」として分けて書く。指摘ゼロなら堂々とゼロと報告する（水増ししない）。

各指摘には `ファイル:行`、重要度、修正案を付ける。
