# レビュー規約

このリポジトリでコードレビューを行うすべての主体（人間・`reviewer` エージェント・別モデルCLIレビュアー）が従う共通規約。**レビュー観点・重要度・design.md の読み方の単一ソース**であり、他の文書はここを参照して再掲しない。

## 読む章（design.md 章マッピング）

レビュー時は、**変更ファイルの領域に対応する `docs/design.md` の章**を読んでから差分を判断する。1500行を超えるため全文は読まない。

| 変更ファイル | 読む章 |
|---|---|
| `apps/web/**` | §7 フロントエンド画面構成 / §8 フロントエンドアーキテクチャ / §9 データフェッチング・整形フロー |
| `apps/api/**` | §4 データモデル / §10 バックエンドアーキテクチャ |
| `packages/shared/**` | §4 データモデル / §10 バックエンドアーキテクチャ |
| `content/**` | §11 コンテンツ規約 |
| テストファイル | フロントは §9.8、バックエンドは §10.9 |
| ビルド・デプロイ・CI 設定 | §12 環境・デプロイ |

複数領域にまたがる場合は該当章をすべて読む。判断に迷う場合は章を広めに取る。`.claude/rules/*.md` が指す章番号（例: 「design.md 8.3」）も併せて参照する。章の行範囲は `grep -n "^## " docs/design.md` と `grep -n "^### " docs/design.md` で確認できる。

## レビュー観点

次の5つを扱う。**優先順は担当するレビュープロファイルによって変わる**（次節）。

1. **仕様準拠**: `docs/design.md` と実装方針・受け入れ条件に沿っているか。
2. **ガードレール違反**: `any` の使用、`packages/shared` 外での型・スキーマの二重定義、Zod バリデーションの欠落、SRS ロジックと副作用の混在、教材本文の D1 直接書き込み。
3. **正確性**: バグ、ロジック誤り、エッジケース（null / 空配列 / 境界値）、非同期処理の誤り。
4. **セキュリティ**: 入力検証漏れ、SQL インジェクション、ユーザー分離の欠落。
5. **テスト**: 新規ロジックにテストがあるか。テストが実質を検証しているか。

## レビュープロファイル

複数のレビュアーを並列に走らせるとき、全員が同じ優先順で読むと同じ見落とし方をする。**プロファイルで優先順を変えて補完させる。** 各レビュアーは自分に割り当てられたプロファイル1つだけを参照する。

### `accuracy-first`（正確性優先）

担当: `reviewer`、および GitHub App 方式で並列実行する1件目の `reviewer`。

優先順: **正確性 → セキュリティ → 仕様準拠 → ガードレール違反 → テスト**

バグ・ロジック誤り・エッジケースを最優先で探す。仕様準拠も見るが、正確性の検証を削ってまで章を読み込まない。

### `spec-compliance-first`（仕様準拠優先）

担当: 別モデルCLIレビュアー（`codex-reviewer` / `claude-reviewer`）、および GitHub App 方式で並列実行する2件目の `reviewer`。

優先順: **仕様準拠 → ガードレール違反 → 正確性 → セキュリティ → テスト**

`docs/design.md` の該当章と受け入れ条件への適合を最優先で検証する。設計から外れた実装は、それ単体でバグがなくても must-fix として扱う。

## 重要度

- **must-fix**: バグ・仕様違反・受け入れ条件の未達・セキュリティ問題・データ破壊の可能性。確信がある場合のみ付ける。
- **should-fix**: ガードレール違反・保守性の問題・エラーハンドリング不足。
- **nit**: スタイル・命名・コメントなど好みの範疇。fix ループには回さない。

## 報告のしかた

推測ベースの指摘はしない。確認できなかった懸念は「確認事項」として分けて書く。指摘ゼロなら堂々とゼロと報告する（水増ししない）。

各指摘には `ファイル:行`、重要度、修正案を付ける。
