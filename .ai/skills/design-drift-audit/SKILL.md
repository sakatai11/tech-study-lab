# design.md 仕様差分監査

実行前に `.ai/runtime-compatibility.md` と `.ai/review-guidelines.md` を全文読む。重要度、`docs/design.md` の章マッピング、報告規約は `.ai/review-guidelines.md` を単一ソースとし、このスキルで再定義しない。

Codexでは開始直後と完了直前に `./.ai/hooks/log-skill-usage.sh --runtime codex --skill design-drift-audit --status started|completed` を実行して共通ログへ記録する（Claudeではhookが自動記録する）。

この監査は読み取り専用で行う。ユーザーが監査後に明示的に承認するまで、ファイル修正、Issue登録、ブランチ作成、コミット、push、PR作成を行わない。

## 入力とモード

対象ブランチは既定で `develop`、設計の一次ソースは `docs/design.md` とする。ユーザーが別のrefまたは期間を明示した場合だけ上書きする。

- `full`: 現在の対象スナップショット全体を監査する。初回監査、長期間未実行、またはユーザーが全体確認を求めた場合に使う。
- `weekly`: 直近7日間に対象ブランチへ入った変更を起点に、関連する設計・実装・テスト・設定・補助資料を監査する。期間指定があれば従う。

モード指定がなく、過去の監査結果から週次継続と確認できる場合は `weekly`、それ以外は `full` とする。推測で過去の監査済み範囲を作らない。

## 1. 対象スナップショットを確定する

1. 現在のブランチ、HEAD SHA、作業ツリー状態、`develop` と `origin/develop` のSHAを確認する。
2. GitHubへの読み取りアクセスが利用できる場合は `origin/develop` をfetchし、監査対象を最新化する。利用できなければ取得済みrefの日時と制約を報告する。
3. 対象スナップショットと異なるブランチや未コミット変更を、監査結果へ混入させない。ブランチ切替、stash、変更破棄は行わない。対象を安全に分離できない場合は監査を `error` として止め、必要な実行条件を報告する。
4. レポート用に対象ref、確定SHA、モード、対象期間を記録する。

`weekly` では対象期間のコミットと変更ファイルを列挙する。変更がない場合も、横断的ガードレールと設計文書間の明白な矛盾を確認してから「差分なし」と報告する。

## 2. 設計上の主張と確認範囲を対応付ける

`docs/design.md` の見出し位置を確認し、`.ai/review-guidelines.md` の章マッピングに従って読む範囲を決める。

### `full`

- 技術スタック、リポジトリ構成、データモデル、API契約、画面構成、レイヤー境界、テスト方針、デプロイ設定など、実装で検証できる設計上の主張を章ごとに整理する。
- `apps/web/`、`apps/api/`、`packages/shared/`、`content/`、設定、テスト、補助資料の対応箇所を追う。
- 将来仕様、スコープ外、未着手と明記された事項を、実装漏れとして扱わない。

### `weekly`

- 対象期間に変更されたファイルを章マッピングへ当て、該当章を読む。
- 変更ファイルだけで判断せず、呼び出し元、共有契約、テスト、設定、関連する補助資料まで追う。
- `docs/design.md` 自体が変更されている場合は、変更された主張が実装済みか、将来仕様か、既存実装と矛盾しないかを確認する。
- 実装だけが変更されている場合は、外部挙動、API契約、データモデル、責務境界など設計へ反映すべき変更かを確認する。

補助資料（`docs/*.html`、`AGENTS.md`、ルール文書）は二次資料として扱う。一次ソースと矛盾する場合は補助資料側の差分候補とし、補助資料を根拠に `docs/design.md` を上書きしない。テストは実装の証拠として使うが、仕様の一次ソースにはしない。

## 3. 双方向に検証する

次の両方向を必ず確認する。

1. **設計 → リポジトリ**: 設計上の主張に対応する実装・契約・設定・テストが存在し、記載どおり動く根拠があるか。
2. **リポジトリ → 設計**: 現在の外部挙動、API契約、データモデル、構成、責務境界が `docs/design.md` に記載されているか。

文字列検索だけで「未実装」と断定しない。定義、利用箇所、公開契約、設定、テストを追い、必要に応じて履歴も確認する。UIの表示や操作に関する主張は利用可能ならブラウザで確認し、利用できなければ未確認と明記する。

各候補を次のいずれかに分類する。

- `design-only`: 現行仕様として記載されているが、対応する実装・設定・テストの根拠がない。
- `implementation-only`: 現在の挙動や契約が実装されているが、一次仕様へ反映されていない。
- `conflict`: 設計とリポジトリが同じ事項について異なる内容を示す。
- `deferred-intentional`: 将来仕様、スコープ外、依存Issue待ちなど、未実装であることが明示されている。
- `aligned`: 設計とリポジトリが整合し、差分候補ではない。

`deferred-intentional` と `aligned` は問題件数へ含めない。根拠不足の候補は断定せず「確認事項」とする。修正方向は「設計を更新」「実装を設計へ合わせる」「人間の判断が必要」のいずれかを根拠付きで提案し、仕様変更を監査者だけで決定しない。

## 4. 検証コマンドを実行する

対象スナップショットを安全に検証でき、依存関係が利用可能な場合は次を実行する。

```bash
pnpm typecheck
pnpm lint
pnpm test
```

品質ゲートの成功だけで仕様整合と判定しない。失敗した場合は仕様差分との関連を確認し、関連が立証できない失敗を監査指摘へ混ぜない。依存関係、認証、ブラウザ、外部サービスなどが不足して実行できない検証は、失敗扱いにせず `not-run` と理由を記録する。監査のためだけに依存関係を追加・更新しない。

## 5. レポートする

次の順で報告する。

1. **監査条件**: モード、対象ref/SHA、対象期間、確認領域。
2. **結論**: `pass` / `findings` / `error` と分類別件数。
3. **指摘**: 各項目にID、分類、重要度、`docs/design.md` の節・行、対象ファイル・行、確認した根拠、影響、推奨する修正方向、確信度を付ける。
4. **確認事項**: 根拠不足または仕様判断が必要な項目。
5. **検証結果**: 実行したコマンドと `pass` / `fail` / `not-run`、ブラウザ確認の有無。
6. **確認済み範囲と制約**: 指摘ゼロの場合も、調べた章・パス・未確認事項を明記する。

同じ原因の差分を複数の指摘に水増ししない。差分がなければ「指摘なし」と明記する。監査後の修正やIssue化を提案してもよいが、実行はユーザー承認後に別タスクとして行う。
