# PR レビュー指摘対応

PRの指摘を現在のコードと仕様に照らして判断し、修正内容または適用しない理由をレビュアーへ返す。進め方は状況に合わせて判断し、以下の不変条件と完了条件を守る。

GitHub 操作は [実行互換ルール](../../runtime-compatibility.md) の「GitHub 操作と認証」に従う。GitHub操作は認証確認済みの `gh` CLI（`gh pr-review` 拡張または `gh api`）を使い、Codex Appでは接続済みGitHubコネクタも利用できる。ローカルの修正・コミット・pushは Git を使う。

Codexでは開始直後と完了直前に `./.ai/hooks/log-skill-usage.sh --runtime codex --skill pr-review-fix --status started|completed` を実行して共通ログへ記録する（Claudeではhookが自動記録する）。

## 不変条件

- **`gh pr merge` は使わない**。マージは常に人間が判断する。本スキルはPRの指摘対応・返信・スレッド解決を扱う。
- 対象PR・リポジトリ・head/baseブランチを確認し、既存のPR作業ブランチで修正・pushする。新規ブランチを作らず、`main` では作業しない。
- 未コミット変更がある場合は今回の修正とユーザー変更を見分ける。ユーザー変更をstash・破棄・コミットしない。区別できない場合は確認してから進める。
- **品質ゲートは返信の前に通す**。変更起因の失敗を解消し、失敗・未実行をpassと報告しない。
- 指摘は現在のコードと仕様で適用可否を判断する。**適用しない指摘にも理由を返信する**。古い指摘や対象範囲外の指摘を黙ってスキップしない。
- 同じコマンド・操作が連続で2回失敗したら、再現手順・ログ・エラーから根本原因を分析して状況を要約し、同じ操作を繰り返さず別の方法を取る。失敗を `|| true` などで隠さない。

## 進め方

1. **指摘の取得**: PRメタデータ、作業ツリー、レビュー スレッド、レビュー本文、通常コメントを確認する。対象コメント・投稿者・ファイル・行・スレッドIDを把握し、未解決の指摘を整理する。取得失敗を「指摘なし」と扱わない。
2. **適用可否の判断**: 指摘箇所と周辺コードを読み、`docs/design.md`・既存パターン・受け入れ条件と照合する。範囲・重要度は [レビュー規約](../../review-guidelines.md) に従う。対象範囲外の問題は別Issue候補として報告し、修正対象に含めない。
3. **修正**: 対象領域の `.ai/rules/*.md` を読んでから、適用する指摘を修正する。仕様との乖離があれば先に `docs/design.md` を更新する。テストの追加・更新はテストルールに従う。`content/` を変更する場合は `content-new` スキルに従う。
4. **品質ゲート**: [issue-dev-orchestrate の「品質ゲート」](../issue-dev-orchestrate/SKILL.md#品質ゲート) を実行する。条件付きゲート、snapshot更新、ベースライン失敗の扱い、テストを弱めない条件も同節に従う。結果と失敗の根拠を記録する。
5. **コミット・push**: 修正ファイルだけを選んでコミットし、対象PRの作業ブランチへpushする。修正がない場合はコミット不要。push失敗時は返信・解決へ進まず、停止状況を報告する。
6. **返信・スレッド解決**: 未解決の指摘に、修正内容とコミット・品質ゲート結果、または適用しない理由を返信する。通常コメントの指摘にも返信する。本文をCLIへ渡す場合は一時ファイルと `--body-file`、または構造化API引数を使う。返信が成功し、指摘への対応が完了したスレッドを解決する。`isOutdated` だけを理由に対応済みとせず、未解決の指摘は現在のコードで判断する。
7. **最終確認**: スレッド・コメントを再取得し、新しい指摘があれば適用判断から繰り返す。待機はユーザーの指示とレビュー状況に応じて判断する。未解決スレッド、返信・pushの成否、作業ツリーを確認し、対応状況を報告する。

## 完了条件と報告

- 対象の未解決指摘すべてに、修正内容または適用しない理由を返信している。
- 修正した場合は、その変更を含むコミットが対象PRへpushされている。修正の有無にかかわらず、品質ゲートの結果が確認できている。
- 対応を終えたスレッドが解決済みで、今回の修正に未コミット変更がない。開始時からのユーザー変更は保持する。

最終報告には、対応した指摘、適用しなかった指摘と理由、品質ゲート結果（ベースライン失敗を含む）、コミットハッシュ、PRのURL、別Issue候補を含める。停止時は、ブランチ・完了した作業・未解決の指摘・残作業を報告し、未完了を完了と扱わない。
