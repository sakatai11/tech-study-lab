# CSRFの仕組みと対策の基本

CSRF（Cross-Site Request Forgery）は、ログイン中の利用者のブラウザを使って、本人が意図していないリクエストを対象サイトに送らせる攻撃です。送金、パスワード変更、メールアドレス変更、退会など、サーバー上の状態を変える操作が狙われます。

XSS が「対象サイトの中で攻撃者のスクリプトを動かす」攻撃だったのに対し、CSRF は「攻撃者の用意した別のページから、対象サイトへリクエストを送らせる」攻撃です。攻撃者は対象サイトのレスポンスを読めませんが、**リクエストを送らせて副作用を起こすだけで目的を達成できる**ことがあります。

## なぜ成立するのか

Web ブラウザには、あるサイト向けのリクエストを送るとき、そのサイトが発行した Cookie を自動的に付けて送る仕組みがあります。この動作は、リクエストを発生させたページがどのサイトのものであっても基本的に同じです。

次のような流れで攻撃が成立します。

1. 被害者が `bank.example` にログインし、セッション Cookie を持っている。
2. 被害者が、同じブラウザで攻撃者のサイト `evil.example` を開く。
3. `evil.example` のページが、`bank.example` へのリクエストを自動で送信する。
4. ブラウザが `bank.example` の Cookie を付けて送信するため、サーバーは正規のログイン済みユーザーからの操作と判断してしまう。

たとえば、攻撃者のページに次のようなフォームがあり、読み込み時に自動送信されるとします。

```html
<form action="https://bank.example/transfer" method="POST" id="f">
  <input type="hidden" name="to" value="attacker" />
  <input type="hidden" name="amount" value="100000" />
</form>
<script>
  document.getElementById('f').submit()
</script>
```

サーバーが「有効なセッション Cookie があれば本人の操作」とだけ判断していると、このリクエストは通ってしまいます。問題はサーバーが **「このリクエストは自サイトの画面から、本人の意思で送られたものか」を確認していない**点にあります。

## GET で状態を変えてはいけない理由

HTTP の仕様では、GET は副作用のない「安全なメソッド」として扱われます。それにもかかわらず、`GET /account/delete` のように状態を変える API を作ると、攻撃はさらに簡単になります。

```html
<img src="https://bank.example/account/delete?confirm=1" />
```

攻撃者は上のようなタグを自サイトやメール、掲示板などに置くだけで、閲覧した被害者のブラウザに GET リクエストを送らせられます。状態変更には POST / PUT / PATCH / DELETE などを使うのが前提です。ただし、メソッドを変えるだけでは CSRF は防げません。先ほどのフォーム例のように POST も外部から送らせられるため、次に述べる対策が別途必要になります。

## 対策1: CSRF トークン

最も基本的な対策は CSRF トークンです。サーバーは、利用者のセッションに紐づく予測困難なトークンを発行し、状態変更リクエストにそのトークンを含めさせます。サーバーは受け取った値を保持している値と照合し、一致しない場合は拒否します。

```html
<form action="/transfer" method="POST">
  <input type="hidden" name="csrf_token" value="<セッションに紐づくランダム値>" />
  ...
</form>
```

攻撃者のページは、被害者向けのトークンの値を知らないため、正しい値を付けたリクエストを作れません。ここで重要なのは、トークンを**ブラウザが自動では付けない場所**（フォームの隠しフィールドやカスタムヘッダー）で送らせることです。Cookie に入れたトークンをサーバーが「届いたかどうか」だけで確認する方式は、Cookie が自動送信されるため意味がありません。

また、トークンを URL のクエリパラメータに載せるのは避けます。URL はブラウザ履歴、サーバーやプロキシのログ、Referer ヘッダーなどを通じて漏れやすいためです。トークンはフォームの本文やリクエストヘッダーで送ります。

なお、同一オリジンに XSS があると、攻撃者のスクリプトがページ内のトークンを読み取って正規のリクエストを送れるため、CSRF トークンも破られます。CSRF 対策は XSS 対策の代わりにはならず、両方が必要です。

## 対策2: SameSite Cookie

SameSite 属性は、クロスサイトのリクエストでブラウザが Cookie を送るかどうかを制御します。

```http
Set-Cookie: session=abc123; Secure; HttpOnly; SameSite=Lax; Path=/
```

- `Strict`: クロスサイトから発生したリクエストでは、リンク遷移も含めて Cookie を送らない。
- `Lax`: クロスサイトの POST フォーム送信や、img・iframe などのサブリソース読み込みでは送らない。ただし、リンクのクリックのようなトップレベルのナビゲーションによる GET では送る。
- `None`: クロスサイトでも送る（`Secure` が必須）。

Chrome や Edge などの Chromium 系ブラウザでは、SameSite 属性を指定しない Cookie を `Lax` 相当で扱います（Cookie 作成直後の短い間は、トップレベルの POST でも送る例外があります）。一方、すべてのブラウザが同じ挙動とは限りません。挙動はブラウザごとに異なるため、既定値に頼らず明示的に指定するのが安全です。

SameSite は強力な防御層ですが、次の限界があります。

- `Lax` では、GET による状態変更はクロスサイトのリンク遷移で攻撃される。
- 「サイト」は登録可能ドメイン（例: `example.com`）単位で判定される。そのため、`a.example.com` と `b.example.com` は同一サイトであり、同じ親ドメインの下にある別サブドメインが乗っ取られたり、攻撃者が利用できたりする場合は防げない。
- 古いブラウザなど、SameSite を正しく扱わない環境がある。

このため、SameSite は CSRF トークンなどの代替ではなく、**多層防御の一つ**として併用します。

## 対策3: Origin / Referer ヘッダーの検証

ブラウザは、クロスオリジンのリクエストや POST リクエストに `Origin` ヘッダー（場合によっては `Referer`）を付けます。サーバー側で、状態変更リクエストの `Origin` が自サイトのオリジンと一致するか検証すると、外部サイトからのリクエストを拒否できます。

```ts
const allowedOrigin = 'https://bank.example'

function isSameOriginRequest(req: Request): boolean {
  const origin = req.headers.get('Origin')
  // Origin が無い場合は Referer など他の手段で判断するか、拒否する方針を決める
  return origin === allowedOrigin
}
```

この方式はトークンの保存が不要な利点がありますが、比較は許可するオリジンとの**完全一致**で行い、前方一致や部分一致（例: `bank.example.evil.example` を通してしまう比較）にしてはいけません。また、`Origin` が無い場合や `null` の場合に通すか拒否するかを事前に決めておく必要があります。`Referer` も省略やポリシーによる削減があり得るため、単独で十分とは考えません。単独ではなく、トークンや SameSite と組み合わせるのが現実的です。

## 対策4: カスタムヘッダーと CORS の関係

API が JSON を受け取る場合、フロントエンドから `X-Requested-With` のようなカスタムヘッダーを付けて送り、サーバーがそのヘッダーの存在を要求する方法があります。

```ts
fetch('/api/transfer', {
  method: 'POST',
  credentials: 'include',
  headers: { 'Content-Type': 'application/json', 'X-Requested-With': 'fetch' },
  body: JSON.stringify({ to: 'alice', amount: 100 }),
})
```

これが機能する理由は CORS のプリフライトにあります。別オリジンのページがカスタムヘッダー付きのリクエストを送ろうとすると、ブラウザは先に `OPTIONS` で許可を確認します。サーバーがそのオリジンを許可していなければ、本体のリクエストは送信されません。単純なフォーム送信では任意のカスタムヘッダーを付けられないため、攻撃者のフォームはこの条件を満たせません。

ただし、これは次の前提が崩れると成立しません。

- CORS の許可オリジンを広げすぎない（`*` や不特定のオリジンを反映する設定にしない）。
- サーバーが、ヘッダーの有無を確実に検証する。

ここで混同しやすいのが、**CORS そのものは CSRF 対策ではない**という点です。CORS が制御するのは、主に別オリジンのスクリプトがレスポンスを読めるかどうかです。フォーム送信のような単純リクエストは CORS の制限を受けずにサーバーに届き、処理も実行されます。「CORS で許可オリジンを絞ったから安全」とは言えません。カスタムヘッダー方式は、プリフライトの副次的な効果を利用した対策の一つであり、CORS の設定だけで成立するものではありません。

## まとめ

- CSRF は、ブラウザが Cookie を自動送信することを悪用し、ログイン中の利用者に意図しない操作をさせる攻撃である。
- 状態変更を GET で行わない。ただし、POST にしただけでは防げない。
- 基本は、予測困難な CSRF トークンをフォーム本文やヘッダーで送らせて照合する方法。
- SameSite Cookie（`Lax` 以上）は有効な追加層だが、GET の遷移やサブドメインなど限界がある。
- Origin / Referer 検証やカスタムヘッダーも併用できる。CORS だけでは CSRF は防げない。
- XSS があると CSRF 対策も回避されるため、XSS 対策と合わせて多層で守る。
