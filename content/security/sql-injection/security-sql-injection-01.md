# SQLインジェクションを防ぐ安全なクエリ構築

SQLインジェクションは、アプリケーションが外部からの入力を SQL 文に組み込む際、その入力によって SQL 文の意味が変えられてしまう脆弱性です。認証の回避、他人のデータの閲覧、データの改ざんや削除などにつながります。

XSS が「データをブラウザが HTML や JavaScript として解釈する」問題だったのに対し、SQLインジェクションは「データをデータベースが SQL の構文として解釈する」問題です。どちらも、**データとコード（構文）の境界が崩れること**が本質です。

## なぜ成立するのか

次のコードは、ユーザーが入力した名前とパスワードでログインを判定します。

```ts
// 危険な例: 入力を文字列連結で SQL に埋め込んでいる
const sql =
  "SELECT * FROM users WHERE name = '" + name + "' AND password = '" + password + "'"
const user = await db.query(sql)
```

通常の入力であれば、期待どおりに動作します。しかし `password` に次のような文字列が入力されたらどうでしょうか。

```text
' OR '1'='1
```

連結後の SQL は次のようになります。

```sql
SELECT * FROM users WHERE name = 'alice' AND password = '' OR '1'='1'
```

SQL では `AND` が `OR` より先に評価されます。そのため `OR '1'='1'` の部分が常に真になり、条件が全行に一致し得ます。結果として、パスワードを知らなくても認証を通過してしまう可能性があります。入力に含まれた引用符が、文字列リテラルを閉じて SQL の構文に変わってしまったことが原因です。

成立の条件は、次の2点が重なることです。

- 入力値が SQL 文字列の一部として組み込まれている（連結、テンプレートリテラルなど）
- その値が、文字列リテラルの外側の構文として解釈され得る

## 情報漏えいへの発展

認証回避だけではありません。検索機能のように結果を画面へ表示する処理では、`UNION` を使って別のテーブルの内容を結果に混ぜる攻撃が考えられます。

```ts
// 危険な例: キーワード検索
const sql = `SELECT title, body FROM articles WHERE title LIKE '%${keyword}%'`
```

攻撃者が `keyword` に引用符と `UNION SELECT ...` を含む文字列を与えると、元の問い合わせの後ろに別の SELECT が連結され、本来見えないはずの列（たとえば他テーブルのメールアドレスなど）が検索結果として返る可能性があります。`UNION` で結合するには列の数や型が揃う必要がありますが、攻撃者は試行錯誤でそれを合わせてきます。「画面に出る部分だけ気をつければよい」という考えは通用しません。

## 根本対策: プレースホルダ（パラメータ化クエリ）

最も重要な対策は、**SQL の構造と値を分離して渡す**ことです。これがプレースホルダ（パラメータ化クエリ、バインド変数）です。SQL 文には値の代わりに `?` や `$1` などの目印だけを書き、値は別に渡します。

Cloudflare D1 の例です。

```ts
const email = url.searchParams.get('email')

// 安全な例: ? と bind() で値を分離する
const user = await env.DB
  .prepare('SELECT id, name FROM users WHERE email = ?')
  .bind(email)
  .first()
```

node-postgres（`pg`）のような一般的なドライバでも考え方は同じです。

```ts
// 安全な例: $1 に値を渡す
const result = await pool.query('SELECT id, name FROM users WHERE email = $1', [email])
```

この方式では、SQL 文の構造はデータベース側で先に確定します。後から渡された値は常に「値」として扱われるため、`' OR '1'='1` を渡しても、それは単なる文字列として比較されるだけです。ログインの例も、次のように書き直すことで防げます。

```ts
const user = await env.DB
  .prepare('SELECT id FROM users WHERE name = ? AND password_hash = ?')
  .bind(name, passwordHash)
  .first()
```

(パスワードを平文で比較する設計自体も避けるべきですが、ここでは SQL の構築方法に焦点を当てています。)

## エスケープの自作やブラックリストに頼らない

「引用符を `''` に置き換えればよい」「`DROP` や `--` が含まれていたら拒否する」といった対策は、一見もっともらしく見えます。しかし次の理由で、根本対策にはなりません。

- データベースの種類や設定、文字コード、文脈（文字列リテラルの中か、数値の位置か）によってエスケープすべき対象が異なり、漏れやすい。
- 大文字小文字の違い、コメント構文、エンコーディングの違いなどで、ブラックリストは回避されやすい。
- 数値として埋め込む場所では、引用符が不要なため、引用符のエスケープが意味を持たない。

「危険な文字を取り除く」のではなく、「入力が構文として解釈される余地を作らない」ことが正しい方向です。

## プレースホルダにできない箇所: 許可リストで対処する

プレースホルダは値の位置にしか使えません。テーブル名、列名、`ORDER BY` の列名や昇順・降順といった識別子・キーワードは、通常プレースホルダにできません。ここで入力を連結すると、再び脆弱になります。

```ts
// 危険な例: sort をそのまま連結
const sql = `SELECT id, title FROM articles ORDER BY ${sort}`
```

この場合は、アプリ側で許可する値を固定し、一致したものだけを使う**許可リスト**方式にします。

```ts
const SORTABLE_COLUMNS = {
  title: 'title',
  created: 'created_at',
} as const

const sortKey = url.searchParams.get('sort') ?? 'created'
const column = SORTABLE_COLUMNS[sortKey as keyof typeof SORTABLE_COLUMNS] ?? 'created_at'
const direction = url.searchParams.get('order') === 'asc' ? 'ASC' : 'DESC'

// SQL に入るのはアプリ側が定義した固定の文字列だけ
const { results } = await env.DB
  .prepare(`SELECT id, title FROM articles ORDER BY ${column} ${direction}`)
  .all()
```

ここで SQL に連結されているのは、入力そのものではなく、入力をキーにして選び出した**アプリ側の固定文字列**です。想定外の入力は既定の列に落とすか、エラーにします。

## ORM・クエリビルダの落とし穴

ORM やクエリビルダの通常の API は、値をパラメータとして扱うため、安全な既定になっています。

```ts
// ORM の通常 API の例（Drizzle）。値はパラメータ化される
const rows = await db.select().from(users).where(eq(users.email, email))
```

しかし、ORM には生 SQL を直接書ける機能があり、そこに入力を連結すると、ORM を使っていても脆弱になります。

```ts
// 危険な例: 生 SQL に入力を連結している
const rows = await db.all(sql.raw(`SELECT * FROM users WHERE email = '${email}'`))
```

生 SQL を使う場合も、そのライブラリが用意している値の渡し方（プレースホルダ指定や、式の中の値を自動でパラメータ化するタグ付きテンプレートなど）を使います。たとえば Drizzle の `sql` テンプレートは、`${}` に渡した値をパラメータとして扱いますが、`sql.raw()` は文字列をそのまま SQL に埋め込むので、入力には使えません。「ORM を使っているから安心」ではなく、「**入力が SQL 文字列に連結される箇所がないか**」を確認する習慣が大切です。

## 多層防御

プレースホルダを正しく使うことが第一ですが、実装ミスに備えて被害を限定する対策も組み合わせます。

- **最小権限**: アプリが使う DB ユーザーには、必要なテーブルへの必要な操作（たとえば SELECT と INSERT のみ）だけを与えます。管理者権限で接続していると、脆弱性が一つあるだけで全データの削除や、スキーマの変更まで許してしまいます。
- **エラーメッセージを出さない**: データベースのエラー詳細（SQL の断片、テーブル名、列名など）は攻撃者の手がかりになります。画面には汎用的なメッセージのみを返し、詳細はサーバー側のログに記録します。
- **入力検証は補助**: 数値のはずの値が数値か、長さや形式が妥当かを確認するのは有用です。ただしこれは不正な値を早く弾く補助であり、すべての入力を安全にするものではありません。たとえば氏名の `O'Brien` のように、正当な入力に引用符が含まれることもあります。入力検証だけに頼らず、必ずプレースホルダで値を渡します。

まとめると、SQLインジェクション対策の基本は「値はプレースホルダ、識別子は許可リスト、生 SQL への連結はしない」です。そのうえで、最小権限とエラー情報の制御で、万一のときの被害を抑えましょう。
