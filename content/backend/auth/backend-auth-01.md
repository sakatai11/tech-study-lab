# 認証と認可の基本とセッション管理

Web アプリのバックエンドでは、リクエストごとに「この人は誰か」「この人にこの操作を許すか」を判断する必要があります。この 2 つを混同すると、ログインさえしていれば何でもできてしまうような API が生まれます。このレッスンでは、認証と認可の違いから、Cookie セッション、JWT、パスワード保存までを順に整理します。

## 認証と認可は別の問い

- **認証（Authentication）**: 「あなたは誰か」を確かめること。パスワードや多要素認証などで本人を識別します。
- **認可（Authorization）**: 「あなたはこの操作をしてよいか」を判断すること。ロールや所有者などの権限をもとに許可します。

HTTP のステータスコードもこの違いに対応します。

| 状況 | ステータス |
| --- | --- |
| 認証情報がない、または無効（未ログイン、期限切れなど） | 401 Unauthorized |
| 本人は識別できているが、操作が許可されていない | 403 Forbidden |

名前が紛らわしいですが、401 は実質的に「未認証」、403 は「認可されていない」と覚えると使い分けやすくなります。

## 認可はサーバーで、毎リクエスト、オブジェクト単位で

次のコードは、ログインしているかどうかだけを確認している危険な例です。

```ts
// 認証は確認しているが、認可がない
app.get('/orders/:id', requireLogin, async (c) => {
  const order = await db.orders.findById(c.req.param('id'))
  return c.json(order)
})
```

ログイン済みなら誰でも `/orders/1`、`/orders/2`、…と ID を変えて他人の注文を取得できます。これが **IDOR（Insecure Direct Object Reference）** です。画面側で他人の注文へのリンクを出さなくても、攻撃者は API を直接呼べるため、UI で隠すことは対策になりません。クライアントはあくまで利用者が操作する場所で、信頼できる境界はサーバーです。

対策は、対象のオブジェクトごとに所有者や権限を検証することです。

```ts
app.get('/orders/:id', requireLogin, async (c) => {
  const user = c.get('user')
  const order = await db.orders.findById(c.req.param('id'))

  // 存在しない場合と他人のものの場合を同じ応答にすると、存在の有無も隠せる
  if (!order || order.ownerId !== user.id) {
    return c.json({ error: 'not found' }, 404)
  }
  return c.json(order)
})
```

ここでは存在しない場合と他人のものの場合を同じ 404 にしています。一方、「見えているが操作が許されない」場合は 403 を返すのが自然です。どちらを採用するかは設計次第ですが、**検証そのものを省かない**ことが重要です。

ポイントは次の 3 つです。

1. 認可は**サーバー側**で行う（UI の出し分けは使い勝手のためで、セキュリティ対策ではない）。
2. **毎リクエスト**検証する（ログイン時に一度確認して終わりにしない）。
3. ロールだけでなく、**対象オブジェクトとの関係**（所有者かどうか）まで確認する。

## Cookie セッションと安全な属性

セッション方式では、ログイン成功時にサーバーがセッション ID を発行し、Cookie に入れてブラウザに渡します。以降のリクエストで Cookie 内のセッション ID からサーバー側のセッション情報を引き当てます。セッション ID は「持っていれば本人として扱われる」秘密情報なので、Cookie の属性で守ります。

```ts
import { setCookie } from 'hono/cookie'

setCookie(c, '__Host-sid', sessionId, {
  httpOnly: true, // JavaScript から読めない
  secure: true, // HTTPS のときだけ送る
  sameSite: 'Lax', // 別サイト起点のリクエストへの送信を制限する
  path: '/',
  maxAge: 60 * 60 * 8,
})
```

- **HttpOnly**: `document.cookie` から読めなくなります。XSS があってもセッション ID そのものは読み出されにくくなります。ただし XSS を防ぐものではありません。
- **Secure**: HTTPS 通信のときだけ Cookie を送ります。平文の HTTP で盗聴されるのを防ぎます。
- **SameSite**: 別サイトから発生したリクエストへの Cookie 送信を制限します。`Lax` は別サイトからの POST などで Cookie を送らず、CSRF のリスクを下げます。ただしトップレベルの GET ナビゲーション（リンクのクリックなど）では Cookie が送られるため、状態を変える処理を GET にしてはいけません。重要な操作には CSRF トークンなど別の対策も組み合わせるのが堅実です。

`__Host-` というプレフィックスを付けると、ブラウザが Secure 属性と `Path=/` を必須とし、Domain 属性を許さないため、設定ミスを防ぎやすくなります。

## ログイン時にセッション ID を再生成する

**セッション固定化（Session Fixation）** は、攻撃者が先に取得した（あるいは自分で決めた）セッション ID を被害者に使わせ、被害者がログインした後に同じ ID で成り済ます攻撃です。ログインの前後でセッション ID が変わらなければ、攻撃者はログイン後の被害者のセッションをそのまま使えてしまいます。

対策は、認証に成功した時点で**新しいセッション ID を発行し、古い ID を無効にする**ことです。

```ts
import { getCookie, setCookie } from 'hono/cookie'

app.post('/login', async (c) => {
  const { email, password } = await c.req.json()
  const user = await verifyCredentials(email, password)
  if (!user) return c.json({ error: 'invalid credentials' }, 401)

  const oldId = getCookie(c, '__Host-sid')
  if (oldId) await sessionStore.destroy(oldId) // 古いセッションを破棄

  const newId = await sessionStore.create({ userId: user.id }) // 新しい ID を発行
  setCookie(c, '__Host-sid', newId, { httpOnly: true, secure: true, sameSite: 'Lax', path: '/' })
  return c.json({ ok: true })
})
```

権限が上がるタイミング（ログイン、管理者への昇格など）で ID を作り直す、と覚えておくとよいでしょう。ログアウト時にもサーバー側のセッションを破棄します。

## JWT の特性と注意点

JWT（JSON Web Token）は、ヘッダー・ペイロード・署名をドット区切りで連結したトークンです。サーバーが状態を持たなくても検証できる便利さがありますが、性質を誤解すると事故につながります。

- **署名は改ざん検知であって暗号化ではない**: 署名付き JWT のペイロードは Base64URL エンコードされているだけで、誰でもデコードして読めます。パスワードや個人情報などの秘密は入れません。
- **即時失効が難しい**: 自己完結型なので、発行済みトークンは `exp` まで有効です。漏えいしても、サーバー側で失効リストなどの仕組みを追加しない限り止められません。対策として、アクセストークンの有効期限を短くし、必要に応じて失効の仕組みを併用します。
- **検証時に許可する `alg` を固定する**: ヘッダーの `alg` は送り手が書ける値です。検証側で許可するアルゴリズムを固定しないと、想定外のアルゴリズム（過去には `none` や、公開鍵を共通鍵として扱わせる攻撃）が使われる恐れがあります。
- **ヘッダーが指す鍵を無条件に信用しない**: ヘッダーの `jwk` や `jku` などが指す鍵を、検証にそのまま使ってはいけません。攻撃者が自分の鍵を指定して署名したトークンを通せてしまうため、検証鍵はサーバー側で管理した信頼できるものに限ります。

```ts
import { jwtVerify } from 'jose'

const { payload } = await jwtVerify(token, secretKey, {
  algorithms: ['HS256'], // 許可するアルゴリズムを明示する
  issuer: 'https://api.example.com', // 発行者も確認する
  requiredClaims: ['exp'], // exp の無い（期限切れにならない）トークンを拒否する
})
// exp は含まれているときだけ検証されるため、requiredClaims で必須にする。期限切れなら例外を投げる
```

JWT を使うか Cookie セッションを使うかはどちらが優れているという話ではなく、失効のしやすさ、スケールのさせやすさ、クライアントの種類などで選びます。ブラウザ中心のアプリでは、HttpOnly Cookie のセッションがシンプルで安全に運用しやすい選択肢です。

## パスワードは遅いハッシュで保存する

パスワードは、データベースが漏えいしても元の値が分かりにくい形で保存します。

- **平文や可逆な暗号化はしない**: 鍵が漏れると全て読まれます。パスワードは復号する必要がなく、入力値のハッシュを保存済みのハッシュと比較すれば十分です。
- **SHA-256 のような高速ハッシュ単体は不向き**: 速いということは、攻撃者が大量の候補を高速に試せるということです。
- **Argon2 や bcrypt などのパスワード用ハッシュを使う**: ソルト（ユーザーごとのランダムな値）を使い、計算コストを調整して意図的に遅くできます。ソルトはハッシュ値に含めて保存されるのが一般的です。

```ts
import argon2 from 'argon2'

const hash = await argon2.hash(password) // ソルトとパラメータはハッシュ文字列に含まれる
// 保存するのは hash のみ

const ok = await argon2.verify(hash, inputPassword)
```

どのアルゴリズムでもコストなどのパラメータは時間とともに見直し、ライブラリが推奨する設定に従います。自前でアルゴリズムを組み合わせるのではなく、実績のあるライブラリの標準的な使い方に従うことが基本です。

## まとめ

- 認証は「誰か」、認可は「何をしてよいか」。未認証は 401、認可されていないのは 403。
- 認可はサーバー側で毎リクエスト、オブジェクトの所有者まで検証する。UI で隠すだけでは IDOR を防げない。
- セッション Cookie には HttpOnly / Secure / SameSite を付け、ログイン時にセッション ID を再生成する。
- JWT の署名は暗号化ではない。有効期限を短くし、`alg` などを検証側で固定する。
- パスワードは Argon2 や bcrypt のような遅いハッシュで保存する。
